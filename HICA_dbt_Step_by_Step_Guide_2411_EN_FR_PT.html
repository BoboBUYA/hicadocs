Build a Data Pipeline with dbt: HICA Step-by-Step Guide

HICA training guide · Prepared 15 November 2026

Welcome: what you will build

By the end of this guide you will have built, by hand and one small step at a time, a data pipeline that turns raw DHIS2 population data into a district-by-year table a dashboard can read, and you will have tested it. You need no dbt or SQL experience. Every command is explained, and every step ends with a check so you know it worked before you move on.

The big picture

Data moves through five layers. Each layer is a little cleaner than the one before it. You will build layers 2 to 5 yourself.

#LayerWhere it livesWhat happens here
1LandingSilo, as compressed JSON filesRaw data exactly as DHIS2 sent it. Already loaded for you. Never edited.
2StagingSilo, as one Parquet fileOne tidy row per value. Columns get proper types. Duplicates are removed.
3IntermediateSilo, as one Parquet fileCodes are replaced by names: indicator names and districts.
4Lake viewClickHouse, as a viewA window onto the Parquet file. Nothing is copied.
5GoldClickHouse, as a tableOne row per district and year, one column per indicator. This is what dashboards read.

Two tools do the work. dbt ("data build tool") runs SQL files in the right order and tests the results. Each SQL file is called a model, and each model builds one table or file. You never write code to "create a table"; you only write a select and dbt does the rest. DuckDB runs the SQL for layers 2 and 3, and ClickHouse runs it for layers 4 and 5. That is why there are two dbt projects: lake (DuckDB) and warehouse (ClickHouse).

What you need before you start

  • A laptop with WSL (Linux on Windows), VS Code, and the project folder Data ingestion with prefect already on it.

  • The Python environment hmis-dbt already installed. To check, open a terminal in VS Code: the line must start with (hmis-dbt), as in step 0.2.

  • Silo (the file store) running on localhost:9100, with its console on localhost:9101.

  • ClickHouse running, with its browser tool at http://localhost:8124/play.

  • The password-like value HMIS_HASH_SALT, which is already in the project's .env file.

  • About three hours, including breaks.

Is this safe for the live pipeline?

Yes, with one thing to watch. Everything you create is named training_... and lives in folders called training, so it never overwrites an existing model. Pause the scheduled Prefect runs before you start (step 1.1), so that nothing runs while you edit. One caution, repeated in step 9: use dbt run -s <model name> and do not put a + in front of the name once your models depend on production models, because the + also rebuilds the production models they read from.

How every step is laid out

Each step has the same four parts, so you always know what to do next.

  1. Why: one or two sentences on what the step teaches.

  2. In VS Code: the file to create or edit, with the exact text to paste. When a step says to replace the file, press Ctrl+A to select everything, paste over it and press Ctrl+S. Never add new code below the old code.

  3. In the terminal: the commands to run, each explained.

  4. Check: what you should see. If you do not see it, stop and use the Troubleshooting section before you continue.

The golden rule of this guide: change one thing, run it, look at the result. Never change three things and then run. When something breaks, you will know exactly which change caused it.

Part 0: Set up your workspace

You will work in two places at once. VS Code is where you create and edit files. The terminal inside VS Code is where you run commands. Spend ten minutes here getting comfortable, because every later step uses these same few moves.

0.1 Open the project in VS Code

  1. Open VS Code.

  2. Look at the bottom-left corner of the window. It should show a blue or green box that says WSL: Ubuntu (or similar). That means VS Code is working inside Linux, where dbt is installed. If you do not see it, click the box, choose Connect to WSL, and wait for the window to reload.

  3. Choose File, then Open Folder, and select the project folder named Data ingestion with prefect. Click OK. If VS Code asks "Do you trust the authors of this folder?", choose Yes, I trust the authors.

  4. On the left you now see the Explorer, a tree of folders. Open dbt. Inside it you will see two folders, lake and warehouse. These are your two dbt projects.

Check: the Explorer shows dbt, and inside it lake and warehouse.

0.2 Open the terminal and activate the Python environment

  1. In VS Code choose Terminal, then New Terminal (or press Ctrl+backtick). A panel opens at the bottom.

  2. Look at the start of the line. If it begins with (hmis-dbt), the Python environment that contains dbt is already active, and you can go on. If it does not, run:

source ~/venvs/hmis-dbt/bin/activate

What it means: source runs a file in your current terminal, and that file switches on a private Python setup called a virtual environment. dbt is installed inside it, so without it the command dbt is not found. The (hmis-dbt) at the start of the line is how you know it is on.

  1. Move into the lake project. The path will be slightly different on your laptop, so type the start of each folder name and press the Tab key to auto-complete it:

cd dbt/lake

What it means: cd means "change directory", that is, move into a folder. The text before the $ at the end of your prompt always shows where you are. After this command it should end in /dbt/lake$.

Check: your prompt starts with (hmis-dbt) and ends with dbt/lake$.

0.4 Create folders and files in VS Code

You will do this many times, and you never need the terminal for it.

  • New folder: in the Explorer, right-click the folder where it should go, choose New Folder, type the name, and press Enter.

  • New file: right-click the folder, choose New File, type the full name including the ending, for example training_stg_population_values.sql, and press Enter. The empty file opens on the right.

  • Type or paste the content, then press Ctrl+S to save. If the tab shows a white dot instead of an x, the file is not saved yet and dbt will not see your change.

  • Copy a file as a backup: right-click it, choose Copy, right-click the folder, choose Paste, then right-click the copy and choose Rename.

Two rules prevent most of the problems we saw in the training room:

  1. Folder names must be typed exactly as the guide says, and they must be nested in the order shown. A file in models/lake/training is a different place from models/training/lake, and dbt treats them differently.

  2. Always check which project you are in. The prompt must say dbt/lake$ for the lake steps and dbt/warehouse$ for the ClickHouse steps. Running a command in the wrong project is the second most common mistake.

0.5 How to read dbt's output

Every dbt command prints a lot of lines. You only need to read three things.

  • The model line. For example OK created sql external model staging.training_stg_population_values. OK means that model was built.

  • The last line: Done. PASS=2 WARN=0 ERROR=0 SKIP=0 TOTAL=2. PASS is good. WARN is a warning that does not stop anything. ERROR means something failed, and the lines just above it say what.

  • Red text. If something is red, read the first red line. It usually names the file and the line number of the problem.

0.6 Two browser tools you will also use

  • Silo console at http://localhost:9101: the file browser for your data lake. Open the bucket hmis-datalake to see the landing, staging and intermediate folders and the files in them.

  • ClickHouse Play at http://localhost:8124/play: a page where you type SQL and see the answer. The address, user and password are filled in at the top. Paste a query into the large box and press Ctrl+Enter to run it. Always select the old text with Ctrl+A first so you run only the new query.

Part 1: Prepare the lake project

Before you write any model, you tell dbt where your training models will live and how to build them. This is a one-time change to one configuration file. Take your time here: a wrong indentation in this file was the number one problem in our own rehearsal.

1.1 Pause the live pipeline (session setup)

The production pipeline runs on a schedule in Prefect and rebuilds the models. Pause it before you start: open the Prefect page, go to Work Pools, open hmis-process-pool, and switch it to Paused. Remember to un-pause it when the session ends (see the last section).

1.2 Make a backup of the project file

In VS Code, open the Explorer, go to dbt/lake, right-click dbt_project.yml, choose Copy, then right-click the lake folder and choose Paste. Right-click the copy, choose Rename, and call it dbt_project.yml.bak. Or, in the terminal inside dbt/lake, run:

cp dbt_project.yml dbt_project.yml.bak

What it means: cp copies a file, so you now have dbt_project.yml.bak beside the original. If you ever break the file, you can copy the backup over it.

Check: run ls in dbt/lake. Both dbt_project.yml and dbt_project.yml.bak appear.

1.3 Tell dbt about the training folder

dbt_project.yml is the settings file of the project. The block under models: says: "models in this folder are built this way." You will add a new block for a folder called training.

  1. Open dbt/lake/dbt_project.yml in VS Code.

  2. Scroll to the very end of the file. The last lines belong to the models: section.

  3. Click on the last line, press Shift+Home to select any spaces before the cursor, and press Delete, so the cursor is at the far left edge. This matters: VS Code often copies the indentation of the line above, which is the wrong amount.

  4. Press Enter to start a new line, then paste this block, exactly as it is, including the spaces at the start of every line:

    training:
      staging:
        +materialized: external
        +format: parquet
        +schema: staging
      intermediate:
        +materialized: external
        +format: parquet
        +schema: intermediate

  1. Press Ctrl+S to save.

Indentation is meaning. In YAML, the number of spaces in front of a line decides which line it belongs to. Use spaces, never the Tab key. The training: line must start in the same column as the other folder names that already exist under hmis_lake:. This is how the structure must look, where the first number is the count of spaces before the text:

 0  models:
 2    hmis_lake:
 4      (existing folders, for example: staging:)
 4      training:                  <- your new block, same column as the folders above
 6        staging:
 8          +materialized: external
 8          +format: parquet
 8          +schema: staging
 6        intermediate:
 8          +materialized: external
 8          +format: parquet
 8          +schema: intermediate

Check by eye: the first letter t of training: is exactly under the first letter of the existing folder names above it. VS Code draws thin vertical guide lines that help you see this. The red wavy lines VS Code puts under YAML words are normal for dbt files and can be ignored.

What each setting means.

SettingWhat it does
training:The folder name. It must match the folder models/training exactly.
staging: and intermediate:The sub-folders. Models inside them get these settings.
+materialized: external"Materialized" is how dbt stores a model. external makes dbt write the result as a real file in Silo instead of a table inside DuckDB.
+format: parquetThe file format. Parquet is a compact, fast format that ClickHouse can also read.
+schema: stagingChooses the Silo folder the file is written to.

1.4 Check the salt

Staging will later store the data-entry user as a hash, a scrambled value that cannot be turned back into the name. The scrambling needs a secret ingredient called a salt, which lives in the environment variable HMIS_HASH_SALT. In the terminal, in dbt/lake, run:

echo ${HMIS_HASH_SALT:+salt is set}

What it means: echo prints text. The odd-looking part prints salt is set only if the variable has a value, and prints nothing if it is empty. It never shows the secret itself.

If it prints nothing, load it from the project's .env file:

export HMIS_HASH_SALT=$(grep '^HMIS_HASH_SALT=' ../../.env | cut -d= -f2-)

What it means: grep finds the line that starts with HMIS_HASH_SALT= in the .env file two folders up, cut keeps only the part after the equals sign, and export stores it in your terminal for this session. If you open a new terminal later, you must run it again.

Never type a value like <the class salt> with the angle brackets: those are a placeholder, not a real value.

1.5 Check that dbt can connect

dbt debug

What it means: dbt debug checks that dbt can read your project files and reach the database. Run it in dbt/lake now and, later, in dbt/warehouse.

Check: the last line says All checks passed!. If not, read the red line above it. The most common causes are a missing .env value or being in the wrong folder.

1.6 Create a small helper to look at results

After every step you will want to look at the first few rows of a model. dbt has a command for that, but it is long, so you will save it as a tiny script.

  1. In dbt/lake, create a folder called hica_steps.

  2. Inside it, create a file called look.sh with this content, then save it:

model="$1"; n="${2:-10}"; cols="${3:-*}"
dbt show --inline "select ${cols} from {{ ref('${model}') }}" --limit "${n}"

What it means: the script takes up to three words after its name. The first is the model name, the second is how many rows to show (10 if you leave it out), and the third is which columns (all of them if you leave it out). It then runs dbt show --inline, which runs a quick select and prints a preview without building anything.

You will use it like this, from dbt/lake:

bash hica_steps/look.sh training_stg_population_values 5

Check: nothing to run yet. You will try it in the first step.

How the helper file is created. look.sh is nothing special: it is a plain text file with two lines in it. You create it exactly like any other file in this guide. In the Explorer, right-click the hica_steps folder, choose New File, type look.sh, paste the two lines, and press Ctrl+S. The ending .sh tells everyone it is a shell script, which means a list of terminal commands saved in a file so you can run them again without retyping. Nothing needs to be installed.

Why we run it with bash hica_steps/look.sh model_name 5. Without the helper, every time you want to look at a model you would have to type this long command:

dbt show --inline "select * from {{ ref('training_stg_population_values') }}" --limit 5

The helper stores that command once, and you only type the short part that changes. Read the short command from left to right:

PartMeaning
bashThe program that reads a script file and runs the commands inside it. Putting bash in front means the file runs without any extra permission setting.
hica_steps/look.shThe path to your file: the folder hica_steps, then the file look.sh. You run it from dbt/lake, so the path starts from there.
training_stg_population_valuesThe first word after the file name. The script receives it as $1. It is the name of the model you want to look at.
5The second word, received as $2: how many rows to show. If you leave it out, the script uses 10.
"period, year" (optional)A third word, received as $3: which columns to show. If you leave it out, the script shows all of them.

Inside the script, model="$1" copies the first word into a name called model. The odd-looking ${2:-10} means "use the second word, and if there is none, use 10", and ${3:-*} means "use the third word, and if there is none, use *, which means all columns". The last line then builds the dbt show command with those values filled in. You will use the helper for the first time in step 1.

Part 2: Build the staging model, steps 1 to 8

Staging turns the raw landing files into one tidy row per data value. You will build it in eight small steps, always editing the same file. Each step replaces the whole file with a slightly better version, so you see exactly what each new line of SQL adds.

Create the folder and the file (do this once)

All commands in this part run in the terminal in dbt/lake (the prompt ends in dbt/lake$).

  1. In the VS Code Explorer, open dbt/lake/models.

  2. Right-click models, choose New Folder, and type training.

  3. Right-click the new training folder, choose New Folder, and type staging. The path is now dbt/lake/models/training/staging.

  4. Right-click staging, choose New File, and type training_stg_population_values.sql.

The folder names training and staging must match the names you wrote in dbt_project.yml in Part 1. That match is how dbt finds the settings for this file.

One rule for steps 1 to 8: you always work in this one file. The file starts empty, so in step 1 you simply paste. From step 2 onwards, each step gives you the complete new version of the file. To use it, click inside the file, press Ctrl+A to select everything, paste the new code so that it overwrites the old code, and press Ctrl+S to save. Do not paste it below the old code, and do not create a new file for each step. If you do, dbt will see two models with the same name, or two queries glued together, and it will fail. The same rule applies to the intermediate file in Part 3 and the gold file in Part 4.

Step 1: Read the raw data

Why: the smallest model possible. It only reads the raw data, so you can see what you are working with.

In VS Code: paste this into training_stg_population_values.sql and press Ctrl+S.

{{ config(materialized='view') }}

select *
from {{ source('landing', 'data_values') }}
where dataset = 'population'

What each part means:

  • {{ ... }} double curly braces mean "dbt, run this before sending the SQL to the database." It is called Jinja.

  • config(materialized='view') tells dbt to store this model as a view, which is only a saved question. It stores no data.

  • source('landing', 'data_values') points at a raw table that dbt did not create. Here it is the landing JSON files in Silo. The project already declares it.

  • where dataset = 'population' keeps only the Population files, because the landing area holds all datasets.

In the terminal:

dbt ls | grep training

dbt ls lists everything dbt can see, and grep training keeps only the lines containing the word training. Check: you see hmis_lake.training.staging.training_stg_population_values. If you only see a warning about unused configuration, dbt cannot see your file. Check the folder names and that you saved.

dbt run -s training_stg_population_values

dbt run builds models. -s means select: build only the model I name. Check: the last line says PASS=1 ... ERROR=0.

bash hica_steps/look.sh training_stg_population_values 5

This prints the first 5 rows. You will see columns such as period, orgUnit, dataValues, filename and run_id. Notice that dataValues holds a whole list of values packed into one cell. That is the problem we solve next.

Two more questions are worth asking the data. First, what columns exist and what are their types?

dbt show --inline "describe select * from {{ ref('training_stg_population_values') }}"

describe lists each column and its type. dataValues shows as a STRUCT, which is a group of named fields stored together. Second, how big is it?

dbt show --inline "select count(distinct filename) as files, count(*) as payloads from {{ ref('training_stg_population_values') }}"

What it means: ref('...') points at another dbt model by name. count(*) counts rows, and count(distinct filename) counts different files. On the reference data this printed 17 files. Your own numbers will match the reference numbers only if you use the same landing data, so do not worry about small differences.

Step 2: Turn the list into rows

Why: one landing row contains many data values. unnest turns the list into one row per value.

In VS Code: replace the whole file. Click inside the file, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file.

{{ config(materialized='view') }}

select
    run_id,
    unnest(dataValues) as dv
from {{ source('landing', 'data_values') }}
where dataset = 'population'

What it means: unnest(dataValues) produces one output row for every item in the list, and as dv names the new column. run_id is the identifier of the load run that brought the file in; we keep it because step 8 needs it.

In the terminal:

dbt run -s training_stg_population_values
bash hica_steps/look.sh training_stg_population_values 3 "dv.*"
bash hica_steps/look.sh training_stg_population_values 1 "count(*) as total_values"

The second command shows what is inside dv: dv.* means "every field of dv, as separate columns". You will see dataElement, period, orgUnit, categoryOptionCombo, value and more. The third command counts the rows. Check: the count is now bigger than the number of files, because every value has its own row. On the reference data it was 25,800.

Step 3: Pick the columns you need

Why: a clean model exposes clear column names, not a packed struct.

In VS Code: replace the whole file. Click inside training_stg_population_values.sql, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file.

{{ config(materialized='view') }}

with unnested as (

    select unnest(dataValues) as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

)

select
    dv.dataElement as data_element_id,
    dv.orgUnit     as org_unit_id,
    dv.value       as value_raw
from unnested

What it means: with unnested as ( ... ) is a CTE, a named step inside the query. You can read the file top to bottom as a recipe: first unnest, then pick columns. dv.dataElement reads the field called dataElement inside dv, and as data_element_id gives it a better name. The _raw suffix reminds us the value is still text.

dbt run -s training_stg_population_values
bash hica_steps/look.sh training_stg_population_values 5
dbt show --inline "select count(*) as empty_org_units from {{ ref('training_stg_population_values') }} where org_unit_id is null"

Check: the last query counts rows with an empty org unit. If it is above 0, the next step fixes that. If it is 0 on your data, the next step is still a good safeguard, because other data sets do have gaps.

Step 4: Fill the gaps

Why: DHIS2 sometimes writes orgUnit and period once on the whole payload instead of on every value. Then the value's own field is empty (NULL).

In VS Code: replace the whole file. Click inside training_stg_population_values.sql, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file.

{{ config(materialized='view') }}

with unnested as (

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

)

select
    dv.dataElement                           as data_element_id,
    dv.categoryOptionCombo                   as category_option_combo_id,
    coalesce(dv.orgUnit, payload_org_unit)   as org_unit_id,
    coalesce(dv.period, payload_period)      as period,
    dv.value                                 as value_raw
from unnested

What it means: coalesce(a, b) returns a, or b if a is empty. So each value uses its own org unit if it has one, and the org unit of the whole payload otherwise.

dbt run -s training_stg_population_values
bash hica_steps/look.sh training_stg_population_values 5
dbt show --inline "select period, count(*) as n from {{ ref('training_stg_population_values') }} group by period order by period"

The last query counts values per period. Check: period is never empty. On the reference data there were two years: 2025 with 10,320 values and 2026 with 15,480.

Step 5: Make the value a number

Why: value_raw is text, and you cannot add up text. We add a numeric version. We also change how the model is stored, from a view to a table.

In VS Code: replace the whole file. Click inside training_stg_population_values.sql, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file.

{{ config(materialized='table') }}

with unnested as (

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

)

select
    dv.dataElement                           as data_element_id,
    dv.categoryOptionCombo                   as category_option_combo_id,
    coalesce(dv.orgUnit, payload_org_unit)   as org_unit_id,
    coalesce(dv.period, payload_period)      as period,
    dv.value                                 as value_raw,
    try_cast(dv.value as double)             as value_numeric
from unnested

What it means: try_cast(x as double) converts text to a decimal number, and gives an empty value instead of crashing when the text is not a number, for example "n/a". The two lines value_raw and value_numeric keep the original and the converted value side by side, so nothing is lost.

A view only saves the question and re-asks it every time. A table stores the answer, so later models read it quickly.

dbt run -s training_stg_population_values
bash hica_steps/look.sh training_stg_population_values 5
dbt show --inline "select count(*) as not_numeric from {{ ref('training_stg_population_values') }} where value_numeric is null and value_raw is not null"

The last query counts texts that could not become numbers. Check: the log line now says table model. On the reference data the count was 0, which means every value was a clean number.

Step 6: Understand the period (your first macro)

Why: the period 2026 is only text. We want to know its type (yearly, monthly, weekly) and its start date. The project already contains macros, reusable pieces of SQL that someone wrote once. You call them by name inside double curly braces.

In VS Code: replace the whole file. Click inside training_stg_population_values.sql, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file.

{{ config(materialized='table') }}

with unnested as (

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

),

restored as (

    select
        dv.dataElement                           as data_element_id,
        dv.categoryOptionCombo                   as category_option_combo_id,
        coalesce(dv.orgUnit, payload_org_unit)   as org_unit_id,
        coalesce(dv.period, payload_period)      as period,
        dv.value                                 as value_raw,
        try_cast(dv.value as double)             as value_numeric
    from unnested

),

typed as (

    select
        *,
        {{ dhis2_period_type('period') }} as period_type
    from restored

)

select
    *,
    {{ dhis2_period_start_date('period', 'period_type') }}         as period_start_date,
    year({{ dhis2_period_start_date('period', 'period_type') }})   as year
from typed

What it means: the file now has three CTEs in a row: unnested, restored, typed. Each one builds on the one before. dhis2_period_type('period') is a macro: it looks at the shape of the text (four digits means yearly) and returns a type. dhis2_period_start_date(...) returns the first day of the period. year(...) extracts the year as a number. select * means "all columns so far".

dbt run -s training_stg_population_values
bash hica_steps/look.sh training_stg_population_values 5 "period, period_type, period_start_date, year"
dbt compile -s training_stg_population_values

dbt compile does not build anything. It prints the real SQL that dbt sends to the database after it replaces every {{ ... }}. Scroll through it: your one-line macro calls have become long case when ... then ... expressions, and source() has become a real read_json(...) call on the Silo files. This is the best way to understand what dbt does for you.

Check: period_type says Yearly, period_start_date is 2025-01-01 or 2026-01-01, and year is 2025 or 2026.

Step 7: Look before you fix (find duplicates)

Why: the landing folder keeps every load run. If a value was loaded twice, or corrected later, it appears more than once. A careful engineer looks for the problem before fixing it. Nothing in your files changes in this step.

dbt show --inline "select data_element_id, org_unit_id, period, category_option_combo_id, count(*) as copies from {{ ref('training_stg_population_values') }} group by all having count(*) > 1" --limit 10

What it means: a single value is identified by four things: the indicator, the org unit, the period and the category combination. group by all groups the rows by those four columns. having count(*) > 1 keeps only the groups that appear more than once. --limit 10 prints at most 10 rows.

Then count the whole picture:

On the reference data it was 25,800 rows against 10,320 distinct values, so every value existed more than once. If both numbers are equal on your data, there are no duplicates today, and step 8 will not change your row count. It is still worth doing, because a future load can bring duplicates.

Step 8: Keep only the newest copy

Why: which copy should we keep? The newest. We rank the copies of each value from newest to oldest and keep number one. We also stop storing the model as a table and let it become a file in Silo.

In VS Code: replace the whole file. Click inside the file, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file. Notice that the config(...) line at the top is gone on purpose.

with unnested as (

    select
        run_id,
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

),

restored as (

    select
        run_id,
        dv.dataElement                           as data_element_id,
        dv.categoryOptionCombo                   as category_option_combo_id,
        coalesce(dv.orgUnit, payload_org_unit)   as org_unit_id,
        coalesce(dv.period, payload_period)      as period,
        dv.value                                 as value_raw,
        try_cast(dv.value as double)             as value_numeric,
        dv.lastUpdated                           as last_updated_raw
    from unnested

),

newest as (

    select *
    from restored
    qualify row_number() over (
        partition by data_element_id, org_unit_id, period, category_option_combo_id
        order by run_id desc, last_updated_raw desc
    ) = 1

),

typed as (

    select *, {{ dhis2_period_type('period') }} as period_type
    from newest

)

select
    *,
    {{ dhis2_period_start_date('period', 'period_type') }}         as period_start_date,
    year({{ dhis2_period_start_date('period', 'period_type') }})   as year
from typed

What it means: row_number() over (partition by ... order by ...) gives a number to the rows inside each group. The partition by lists the four columns that identify one value, so each value forms its own group. order by run_id desc, last_updated_raw desc puts the newest copy first (desc means descending, biggest first). qualify ... = 1 keeps only the row numbered 1 in each group. Step 10: Join in the indicator names

Why: a join looks up each code in another table and brings back the name that belongs to it. Here we look up each data_element_id in stg_dhis2__data_elements, a model your production pipeline already built.

In VS Code: replace the whole file. Click inside the file, press Ctrl+A to select everything, paste the code below so that it overwrites the old code, and press Ctrl+S. Do not add it below the old code and do not create a new file.

select
    p.year,
    p.org_unit_id,
    de.data_element_name,
    p.value_numeric
from {{ ref('training_stg_population_values') }} as p
left join {{ ref('stg_dhis2__data_elements') }} as de
    on de.data_element_id = p.data_element_id

What it means:

  • as p and as de are short nicknames for the two tables, so you can write p.year and de.data_element_name.

  • left join keeps every row from the left table (your population values), even when no name is found. In that case the name is left empty. An ordinary join would silently drop those rows, which is dangerous.

  • on de.data_element_id = p.data_element_id says how the two tables match: the codes must be equal.

In the terminal: from now on, name the models you want to build and do not use the +. Your intermediate model now depends on production models, and a + would rebuild them too.

    toYear(ifNull(period_start_date, toDate32('1970-01-01')))  as year,
    ifNull(district_name, '')                                  as district_name,

What each part means:

  • ref('training_lake_population') points at your ClickHouse view, so dbt builds the view first and the table second.

  • group by plus sum() collapses many rows into one row for every district, year and indicator, and adds their values.

  • config(order_by = ...) sets the sort key of the table. ClickHouse tables must be sorted on something, and sorting on year and district makes the typical dashboard filters fast.

  • ifNull(x, y) means "x, or y if x is empty". A ClickHouse sort key may not contain empty values, so we fill the gaps. toYear(...) extracts the year from a date.

  • This model is a table, not a view, because the gold settings you added say so. The result is stored, so dashboards read it quickly and do not read the Parquet file every time.

Part 5: Test your models, step 15

A pipeline that runs is not the same as a pipeline that is right. Tests are small automatic checks that run on your data every time. If the data breaks a rule, the test says so before a wrong number reaches a dashboard.

dbt has two kinds of tests:

KindWhere you write itHow it works
Generic testIn a .yml file next to your modelsYou attach a ready-made rule to a column, such as not_null (no empty values) or accepted_values (only allowed values).
Singular testA .sql file in the tests folderYou write a query that returns the bad rows. If it returns nothing, the test passes.

A test result is PASS, WARN (a rule is broken but marked as a warning) or FAIL (a rule is broken and marked as an error).

Step 15a: Generic tests for the lake models

In VS Code, in dbt/lake/models/training, create a file called _training__models.yml. It sits directly inside training, next to the staging and intermediate folders. Paste and save:

version: 2

models:
  - name: training_stg_population_values
    columns:
      - name: data_element_id
        data_tests: [not_null]
      - name: org_unit_id
        data_tests: [not_null]

              arguments: {values: ['Yearly']}

          - not_null:

What it means: each - name: under models is a model, and each - name: under columns is one of its columns. data_tests lists the rules for that column. Step 15d: Tests for the ClickHouse models

In the terminal, move to the warehouse: cd ../warehouse.

with production as (
    select
        toYear(ifNull(period_start_date, toDate32('1970-01-01')))   as year,
        ifNull(district_name, '')                                   as district_name,
        sumIf(value_numeric, data_element_name = 'Total population < 1 year') as under1_population
    from {{ ref('lake_dhis2__data_values') }}
    where data_set_name = 'Population' and period_type = 'Yearly'
    group by year, district_name
)
select t.year, t.district_name, t.under1_population, p.under1_population as production_value
from {{ ref('training_fct_population_district_year') }} as t
inner join production as p on p.year = t.year and p.district_name = t.district_name
where abs(t.under1_population - p.under1_population) > 0.5

What it means: this is the most valuable test in the guide. It computes the same figure from the production pipeline and compares it with your training table. It returns the districts where the two disagree by more than 0.5. If your small pipeline and the real one agree everywhere, the result is empty and the test passes.

Check: PASS=4 WARN=0 ERROR=0 on the reference data. If the comparison test fails, the output shows which districts differ. Your gold table does not agree with production for those districts, so look at the indicator names and the district names first.

Step 15e: See a test fail on purpose

Now every group counts as bad, so the test returns many rows and shows FAIL with the number of rows it found. That is what a broken rule looks like. Change >= back to >, save, and run it again to see it pass. Nothing about your data was changed.

Construire un pipeline de données avec dbt : guide étape par étape HICA

Guide de formation HICA · Préparé le 15 novembre 2026

Bienvenue : ce que vous allez construire

À la fin de ce guide, vous aurez construit, à la main et par petites étapes, un pipeline de données qui transforme les données brutes de population de DHIS2 en une table par district et par année que peut lire un tableau de bord, et vous l'aurez testé. Aucune expérience de dbt ni de SQL n'est nécessaire. Chaque commande est expliquée, et chaque étape se termine par une vérification, pour que vous sachiez que cela a fonctionné avant de passer à la suite.

Vue d'ensemble

Les données traversent cinq couches. Chaque couche est un peu plus propre que la précédente. Vous construirez vous-même les couches 2 à 5.

#CoucheOù elle se trouveCe qui s'y passe
1LandingSilo, sous forme de fichiers JSON compressésDonnées brutes, exactement telles que DHIS2 les a envoyées. Déjà chargées pour vous. Jamais modifiées.
2StagingSilo, sous forme d'un fichier ParquetUne ligne propre par valeur. Les colonnes reçoivent les bons types. Les doublons sont supprimés.
3IntermédiaireSilo, sous forme d'un fichier ParquetLes codes sont remplacés par des noms : noms des indicateurs et des districts.
4Vue du lakeClickHouse, sous forme de vueUne fenêtre sur le fichier Parquet. Rien n'est copié.
5GoldClickHouse, sous forme de tableUne ligne par district et par année, une colonne par indicateur. C'est ce que lisent les tableaux de bord.

Deux outils font le travail. dbt (« data build tool ») exécute des fichiers SQL dans le bon ordre et teste les résultats. Chaque fichier SQL s'appelle un modèle, et chaque modèle construit une table ou un fichier. Vous n'écrivez jamais de code pour « créer une table » : vous écrivez seulement un select et dbt fait le reste. DuckDB exécute le SQL des couches 2 et 3, et ClickHouse l'exécute pour les couches 4 et 5. C'est pourquoi il y a deux projets dbt : lake (DuckDB) et warehouse (ClickHouse).

Ce dont vous avez besoin avant de commencer

  • Un ordinateur portable avec WSL (Linux sous Windows), VS Code, et le dossier de projet Data ingestion with prefect déjà présent.

  • L'environnement Python hmis-dbt déjà installé. Pour vérifier, ouvrez un terminal dans VS Code : la ligne doit commencer par (hmis-dbt), comme à l'étape 0.2.

  • Silo (le stockage de fichiers) en marche sur localhost:9100, avec sa console sur localhost:9101.

  • ClickHouse en marche, avec son outil de navigateur à l'adresse http://localhost:8124/play.

  • La valeur de type mot de passe HMIS_HASH_SALT, déjà présente dans le fichier .env du projet.

  • Environ trois heures, pauses comprises.

Est-ce sans risque pour le pipeline en production ?

Oui, à une condition. Tout ce que vous créez s'appelle training_... et se trouve dans des dossiers nommés training, donc rien n'écrase un modèle existant. Mettez en pause les exécutions Prefect planifiées avant de commencer (étape 1.1), afin que rien ne s'exécute pendant que vous modifiez. Une précaution, répétée à l'étape 9 : utilisez dbt run -s <model name> et ne mettez pas de + devant le nom dès que vos modèles dépendent de modèles de production, car le + reconstruit aussi les modèles de production dont ils dépendent.

Comment chaque étape est présentée

Chaque étape comporte les mêmes quatre parties, pour que vous sachiez toujours quoi faire ensuite.

  1. Pourquoi : une ou deux phrases sur ce qu'enseigne l'étape.

  2. Dans VS Code : le fichier à créer ou à modifier, avec le texte exact à coller. Quand une étape dit de remplacer le fichier, appuyez sur Ctrl+A pour tout sélectionner, collez par-dessus et appuyez sur Ctrl+S. N'ajoutez jamais de nouveau code sous l'ancien.

  3. Dans le terminal : les commandes à exécuter, chacune expliquée.

  4. Vérification : ce que vous devez voir. Si vous ne le voyez pas, arrêtez-vous et consultez la section Dépannage avant de continuer.

La règle d'or de ce guide : changez une seule chose, exécutez, regardez le résultat. Ne changez jamais trois choses avant d'exécuter. Quand quelque chose casse, vous saurez exactement quel changement en est la cause.

0.5 Comment lire la sortie de dbt

Chaque commande dbt affiche beaucoup de lignes. Vous n'avez besoin de lire que trois choses.

  • La ligne du modèle. Par exemple OK created sql external model staging.training_stg_population_values. OK signifie que ce modèle a été construit.

  • Le texte rouge. Si quelque chose est en rouge, lisez la première ligne rouge. Elle indique généralement le fichier et le numéro de ligne du problème.

1.4 Vérifier le sel

Le staging stockera plus tard l'utilisateur de la saisie sous forme de hash, une valeur brouillée qu'on ne peut pas reconvertir en nom. Le brouillage nécessite un ingrédient secret appelé sel (« salt »), qui se trouve dans la variable d'environnement HMIS_HASH_SALT. Dans le terminal, dans dbt/lake, exécutez :

echo ${HMIS_HASH_SALT:+salt is set}

Ce que cela signifie : echo affiche du texte. La partie d'apparence étrange affiche salt is set seulement si la variable a une valeur, et n'affiche rien si elle est vide. Elle n'affiche jamais le secret lui-même.

Si rien ne s'affiche, chargez-la depuis le fichier .env du projet :

export HMIS_HASH_SALT=$(grep '^HMIS_HASH_SALT=' ../../.env | cut -d= -f2-)

Ce que cela signifie : grep trouve la ligne qui commence par HMIS_HASH_SALT= dans le fichier .env situé deux dossiers plus haut, cut ne garde que la partie après le signe égal, et export la stocke dans votre terminal pour cette session. Si vous ouvrez un nouveau terminal plus tard, vous devrez la réexécuter.

Ne tapez jamais une valeur comme <the class salt> avec les chevrons : c'est un espace réservé, pas une vraie valeur.

1.6 Créer un petit assistant pour consulter les résultats

Après chaque étape, vous voudrez regarder les premières lignes d'un modèle. dbt a une commande pour cela, mais elle est longue ; vous allez donc l'enregistrer sous forme de minuscule script.

  1. Dans dbt/lake, créez un dossier appelé hica_steps.

  2. À l'intérieur, créez un fichier appelé look.sh avec ce contenu, puis enregistrez-le :

model="$1"; n="${2:-10}"; cols="${3:-*}"
dbt show --inline "select ${cols} from {{ ref('${model}') }}" --limit "${n}"

Ce que cela signifie : le script accepte jusqu'à trois mots après son nom. Le premier est le nom du modèle, le deuxième est le nombre de lignes à afficher (10 si vous l'omettez) et le troisième désigne les colonnes (toutes si vous l'omettez). Il exécute ensuite dbt show --inline, qui lance un select rapide et affiche un aperçu sans rien construire.

Vous l'utiliserez ainsi, depuis dbt/lake :

bash hica_steps/look.sh training_stg_population_values 5

Vérification : rien à exécuter pour l'instant. Vous l'essaierez à la première étape.

Comment le fichier assistant est créé. look.sh n'a rien de spécial : c'est un simple fichier texte de deux lignes. Vous le créez exactement comme n'importe quel autre fichier de ce guide. Dans l'Explorer, faites un clic droit sur le dossier hica_steps, choisissez New File, tapez look.sh, collez les deux lignes et appuyez sur Ctrl+S. L'extension .sh indique à tout le monde qu'il s'agit d'un script shell, c'est-à-dire une liste de commandes de terminal enregistrée dans un fichier pour pouvoir les relancer sans les retaper. Rien n'a besoin d'être installé.

Pourquoi on l'exécute avec bash hica_steps/look.sh model_name 5. Sans l'assistant, chaque fois que vous voudriez consulter un modèle, vous devriez taper cette longue commande :

dbt show --inline "select * from {{ ref('training_stg_population_values') }}" --limit 5

L'assistant enregistre cette commande une fois pour toutes, et vous ne tapez que la courte partie qui change. Lisez la commande courte de gauche à droite :

Étape 4 : Combler les lacunes

Pourquoi : DHIS2 écrit parfois orgUnit et period une seule fois pour toute la charge utile (« payload ») au lieu de les écrire sur chaque valeur. Le champ propre à la valeur est alors vide (NULL).

Dans VS Code : remplacez tout le fichier. Cliquez dans training_stg_population_values.sql, appuyez sur Ctrl+A pour tout sélectionner, collez le code ci-dessous de façon qu'il écrase l'ancien code, puis appuyez sur Ctrl+S. Ne l'ajoutez pas sous l'ancien code et ne créez pas de nouveau fichier.

{{ config(materialized='view') }}

with unnested as (

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

)

select
    dv.dataElement                           as data_element_id,
    dv.categoryOptionCombo                   as category_option_combo_id,
    coalesce(dv.orgUnit, payload_org_unit)   as org_unit_id,

from unnested

Ce que cela signifie : coalesce(a, b) renvoie a, ou b si a est vide. Ainsi, chaque valeur utilise sa propre unité d'organisation si elle en a une, et celle de toute la charge utile sinon.

Étape 5 : Transformer la valeur en nombre

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,

Étape 7 : Regarder avant de corriger (trouver les doublons)

Pourquoi : le dossier landing conserve chaque exécution de chargement. Si une valeur a été chargée deux fois, ou corrigée plus tard, elle apparaît plusieurs fois. Un ingénieur rigoureux cherche le problème avant de le corriger. Rien ne change dans vos fichiers à cette étape.

dbt show --inline "select data_element_id, org_unit_id, period, category_option_combo_id, count(*) as copies from {{ ref('training_stg_population_values') }} group by all having count(*) > 1" --limit 10

Ce que cela signifie : une valeur est identifiée par quatre éléments : l'indicateur, l'unité d'organisation, la période et la combinaison de catégories. group by all regroupe les lignes selon ces quatre colonnes. having count(*) > 1 ne garde que les groupes qui apparaissent plus d'une fois. --limit 10 affiche au plus 10 lignes.

Comptez ensuite l'ensemble :

dbt show --inline "select count(*) as rows_total, count(distinct (data_element_id, org_unit_id, period, category_option_combo_id)) as distinct_values from {{ ref('training_stg_population_values') }}"

Lisez le résultat honnêtement. Si rows_total est supérieur à distinct_values, la différence correspond au nombre de copies en trop. Sur les données de référence, il y avait 25 800 lignes pour 10 320 valeurs distinctes : chaque valeur existait donc plusieurs fois. Si les deux nombres sont égaux sur vos données, il n'y a aucun doublon aujourd'hui, et l'étape 8 ne changera pas votre nombre de lignes. Elle reste utile, car un futur chargement peut apporter des doublons.

Pourquoi : quelle copie garder ? La plus récente. Nous classons les copies de chaque valeur de la plus récente à la plus ancienne et gardons la première. Nous arrêtons aussi de stocker le modèle sous forme de table et le laissons devenir un fichier dans Silo.

Étape 10 : Joindre les noms des indicateurs

Pourquoi : une jointure (join) cherche chaque code dans une autre table et rapporte le nom qui lui correspond. Ici, nous cherchons chaque data_element_id dans stg_dhis2__data_elements, un modèle que votre pipeline de production a déjà construit.

Dans VS Code : remplacez tout le fichier. Cliquez dans le fichier, appuyez sur Ctrl+A pour tout sélectionner, collez le code ci-dessous de façon qu'il écrase l'ancien code, puis appuyez sur Ctrl+S. Ne l'ajoutez pas sous l'ancien code et ne créez pas de nouveau fichier.

select
    p.year,
    p.org_unit_id,
    de.data_element_name,
    p.value_numeric
from {{ ref('training_stg_population_values') }} as p
left join {{ ref('stg_dhis2__data_elements') }} as de
    on de.data_element_id = p.data_element_id

Ce que cela signifie :

  • as p et as de sont de courts surnoms pour les deux tables, ce qui vous permet d'écrire p.year et de.data_element_name.

  • left join (jointure à gauche) garde chaque ligne de la table de gauche (vos valeurs de population), même quand aucun nom n'est trouvé. Dans ce cas, le nom reste vide. Un simple join supprimerait ces lignes en silence, ce qui est dangereux.

  • on de.data_element_id = p.data_element_id indique comment les deux tables se correspondent : les codes doivent être égaux.

Dans le terminal : à partir de maintenant, nommez les modèles que vous voulez construire et n'utilisez pas le +. Votre modèle intermédiaire dépend désormais de modèles de production, et un + les reconstruirait eux aussi.

La dernière requête est votre contrôle de sécurité sur la jointure : n doit être égal au nombre de lignes que vous aviez en staging après l'étape 8 (10 320 sur les données de référence). Si n est supérieur, la jointure a multiplié les lignes : vous devez vous arrêter et en trouver la cause. with_name indique combien de codes ont trouvé leur nom ; s'il est inférieur à n, certains codes n'ont pas de nom.

Étape 13 : Votre première table gold

Pourquoi : gold est la table que lit un tableau de bord. La vue donne une ligne par valeur. Maintenant, nous additionnons les valeurs par district, par année et par indicateur, et ClickHouse stocke le résultat.

Dans VS Code : créez le dossier gold au bon endroit. Faites un clic droit sur le dossier training (celui qui se trouve directement sous models, à côté de lake), choisissez New Folder et tapez gold. Le chemin doit être dbt/warehouse/models/training/gold. Faites ensuite un clic droit sur gold, choisissez New File, tapez training_fct_population_district_year.sql, collez ceci et enregistrez :

{{ config(order_by = '(year, district_name)') }}

select
    toYear(ifNull(period_start_date, toDate32('1970-01-01')))  as year,
    ifNull(district_name, '')                                  as district_name,
    data_element_name,
    sum(value_numeric)                                         as value
from {{ ref('training_lake_population') }}
group by year, district_name, data_element_name

Ce que signifie chaque partie :

  • ref('training_lake_population') pointe vers votre vue ClickHouse : dbt construit donc la vue d'abord et la table ensuite.

  • group by avec sum() condense de nombreuses lignes en une ligne pour chaque district, année et indicateur, et additionne leurs valeurs.

  • config(order_by = ...) définit la clé de tri de la table. Les tables ClickHouse doivent être triées selon quelque chose, et un tri par année et par district rend rapides les filtres typiques d'un tableau de bord.

  • ifNull(x, y) signifie « x, ou y si x est vide ». Une clé de tri ClickHouse ne peut pas contenir de valeurs vides, donc nous comblons les lacunes. toYear(...) extrait l'année d'une date.

  • Ce modèle est une table, et non une vue, parce que les paramètres gold que vous avez ajoutés le prévoient. Le résultat est stocké : les tableaux de bord le lisent donc rapidement et ne relisent pas le fichier Parquet à chaque fois.

Dans le terminal (dans dbt/warehouse) :

dbt run -s training_fct_population_district_year

Vérification : la ligne du journal indique sql table model `gold`.`training_fct_population_district_year` et l'avertissement sur la configuration inutilisée a disparu. Ensuite, dans ClickHouse Play (appuyez sur Ctrl+A avant de coller) :

Étape 14 : Une colonne par indicateur (pivot)

Pourquoi : un tableau de bord veut une ligne par district et par année, avec une colonne distincte pour chaque indicateur, et non cinq lignes. Transformer des lignes en colonnes s'appelle un pivot.

Commencez par découvrir les noms exacts des indicateurs dans vos données, car le pivot doit les écrire exactement. Dans Play :

select data_element_name, count(*) as n from lake.training_lake_population group by data_element_name order by data_element_name

Sur les données de référence, les cinq noms étaient :

Nom de l'indicateur dans les donnéesColonne que nous allons créer
Total Populationtotal_population
Total population < 1 yearunder1_population
Total population < 5 yearsunder5_population
Population of women of child bearing age (WRA)women_of_child_bearing_age
Expected pregnanciesexpected_pregnancies

Dans VS Code : ouvrez le même fichier gold et remplacez tout le fichier. Cliquez dedans, appuyez sur Ctrl+A pour tout sélectionner, collez le code ci-dessous de façon qu'il écrase l'ancien code, puis appuyez sur Ctrl+S. Ne l'ajoutez pas sous l'ancien code et ne créez pas de nouveau fichier. Si vos noms diffèrent, modifiez le texte entre guillemets pour qu'il corresponde à votre propre liste.

{{ config(order_by = '(year, district_name)') }}

select
    toYear(ifNull(period_start_date, toDate32('1970-01-01')))  as year,
    ifNull(district_name, '')                                  as district_name,
    sumIf(value_numeric, data_element_name = 'Total Population')                                as total_population,
    sumIf(value_numeric, data_element_name = 'Total population < 1 year')                       as under1_population,
    sumIf(value_numeric, data_element_name = 'Total population < 5 years')                      as under5_population,
    sumIf(value_numeric, data_element_name = 'Population of women of child bearing age (WRA)')  as women_of_child_bearing_age,
    sumIf(value_numeric, data_element_name = 'Expected pregnancies')                            as expected_pregnancies,
    count()                                                                                     as value_count
from {{ ref('training_lake_population') }}
group by year, district_name

Ce que cela signifie : sumIf(value, condition) additionne uniquement les lignes pour lesquelles la condition est vraie. Chaque colonne demande le total d'un indicateur, de sorte qu'une seule ligne contient désormais les cinq. count() indique combien de valeurs ont alimenté chaque ligne. Faites attention à l'orthographe et aux majuscules : le premier nom est Total Population avec un P majuscule, alors que les autres utilisent un p minuscule. Un nom qui ne correspond pas ne provoque pas d'erreur. Il donne silencieusement 0 ; vérifiez donc que chaque colonne affiche un vrai nombre.

Comparez avec la table longue de l'étape 13 : le même district, la même année et le même indicateur doivent donner le même nombre dans les deux. Pour Bo en 2025, l'exécution de référence a montré 523 015 pour total_population et 23 012 pour expected_pregnancies dans les deux versions : le pivot n'a donc rien perdu.

Partie 5 : Tester vos modèles, étape 15

Un pipeline qui s'exécute n'est pas forcément un pipeline juste. Les tests sont de petites vérifications automatiques exécutées à chaque fois sur vos données. Si les données enfreignent une règle, le test le signale avant qu'un chiffre faux n'atteigne un tableau de bord.

dbt propose deux types de tests :

TypeOù l'écrireComment cela fonctionne
Test génériqueDans un fichier .yml à côté de vos modèlesVous attachez une règle prête à l'emploi à une colonne, comme not_null (aucune valeur vide) ou accepted_values (uniquement des valeurs autorisées).
Test singulierUn fichier .sql dans le dossier testsVous écrivez une requête qui renvoie les lignes erronées. Si elle ne renvoie rien, le test réussit.

Le résultat d'un test est PASS, WARN (une règle est enfreinte mais marquée comme avertissement) ou FAIL (une règle est enfreinte et marquée comme erreur).

Étape 15a : Tests génériques pour les modèles lake

Dans VS Code, dans dbt/lake/models/training, créez un fichier appelé _training__models.yml. Il se trouve directement dans training, à côté des dossiers staging et intermediate. Collez et enregistrez :

version: 2

models:
  - name: training_stg_population_values
    columns:
      - name: data_element_id
        data_tests: [not_null]
      - name: org_unit_id
        data_tests: [not_null]
      - name: period_type
        data_tests:
          - accepted_values:
              arguments: {values: ['Yearly']}
              config: {severity: warn}
      - name: value_numeric
        data_tests:
          - not_null:
              config: {severity: warn}

  - name: training_int_population_by_district
    columns:
      - name: data_element_name
        data_tests: [not_null]
      - name: district_name
        data_tests:
          - not_null:
              config: {severity: warn}

Ce que cela signifie : chaque - name: sous models est un modèle, et chaque - name: sous columns est l'une de ses colonnes. data_tests liste les règles de cette colonne. Les règles marquées severity: warn signalent un problème sans rien arrêter. Par exemple, une valeur non numérique mérite d'être connue, mais ce n'est pas une catastrophe.

Puis, dans dbt/warehouse/tests, créez assert_training_population_matches_production.sql :

with production as (
    select
        toYear(ifNull(period_start_date, toDate32('1970-01-01')))   as year,
        ifNull(district_name, '')                                   as district_name,
        sumIf(value_numeric, data_element_name = 'Total population < 1 year') as under1_population
    from {{ ref('lake_dhis2__data_values') }}
    where data_set_name = 'Population' and period_type = 'Yearly'
    group by year, district_name
)
select t.year, t.district_name, t.under1_population, p.under1_population as production_value
from {{ ref('training_fct_population_district_year') }} as t
inner join production as p on p.year = t.year and p.district_name = t.district_name
where abs(t.under1_population - p.under1_population) > 0.5

Ce que cela signifie : c'est le test le plus précieux du guide. Il calcule le même chiffre à partir du pipeline de production et le compare à votre table d'entraînement. Il renvoie les districts pour lesquels les deux divergent de plus de 0,5. Si votre petit pipeline et le vrai concordent partout, le résultat est vide et le test réussit.

dbt test -s training_fct_population_district_year assert_training_population_matches_production

Vérification : PASS=4 WARN=0 ERROR=0 sur les données de référence. Si le test de comparaison échoue, la sortie montre quels districts diffèrent. Votre table gold ne concorde pas avec la production pour ces districts ; regardez d'abord les noms des indicateurs et les noms des districts.

Étape 15e : Voir un test échouer volontairement

Les apprenants doivent voir un échec une fois, dans un endroit sûr. Dans dbt/lake/tests/assert_training_population_grain_is_unique.sql, remplacez having count(*) > 1 par having count(*) >= 1, enregistrez, et relancez le test depuis dbt/lake :

Construa um pipeline de dados com dbt: guia passo a passo da HICA

Guia de formação da HICA · Preparado em 15 de novembro de 2026

Boas-vindas: o que você vai construir

Ao final deste guia, você terá construído, manualmente e em pequenos passos, um pipeline de dados que transforma os dados brutos de população do DHIS2 em uma tabela por distrito e por ano que um painel pode ler, e o terá testado. Não é preciso ter experiência com dbt ou SQL. Cada comando é explicado, e cada passo termina com uma verificação, para que você saiba que funcionou antes de seguir em frente.

Visão geral

Os dados passam por cinco camadas. Cada camada é um pouco mais limpa que a anterior. Você mesmo construirá as camadas 2 a 5.

#CamadaOnde ficaO que acontece aqui
1LandingSilo, como arquivos JSON compactadosDados brutos exatamente como o DHIS2 os enviou. Já carregados para você. Nunca editados.
2StagingSilo, como um arquivo ParquetUma linha limpa por valor. As colunas recebem os tipos corretos. Os duplicados são removidos.
3IntermediáriaSilo, como um arquivo ParquetOs códigos são substituídos por nomes: nomes de indicadores e de distritos.
4View do lakeClickHouse, como uma viewUma janela para o arquivo Parquet. Nada é copiado.
5GoldClickHouse, como uma tabelaUma linha por distrito e ano, uma coluna por indicador. É isso que os painéis leem.

Duas ferramentas fazem o trabalho. O dbt (“data build tool”) executa arquivos SQL na ordem certa e testa os resultados. Cada arquivo SQL é chamado de modelo, e cada modelo constrói uma tabela ou um arquivo. Você nunca escreve código para “criar uma tabela”: escreve apenas um select e o dbt faz o resto. O DuckDB executa o SQL das camadas 2 e 3, e o ClickHouse o executa nas camadas 4 e 5. Por isso existem dois projetos dbt: lake (DuckDB) e warehouse (ClickHouse).

O que você precisa antes de começar

  • Um laptop com WSL (Linux no Windows), VS Code e a pasta do projeto Data ingestion with prefect já nele.

  • O ambiente Python hmis-dbt já instalado. Para verificar, abra um terminal no VS Code: a linha deve começar com (hmis-dbt), como no passo 0.2.

  • O Silo (o armazenamento de arquivos) em execução em localhost:9100, com seu console em localhost:9101.

  • O ClickHouse em execução, com sua ferramenta de navegador em http://localhost:8124/play.

  • O valor semelhante a uma senha HMIS_HASH_SALT, que já está no arquivo .env do projeto.

  • Cerca de três horas, incluindo as pausas.

Isto é seguro para o pipeline em produção?

Sim, com um cuidado. Tudo o que você cria se chama training_... e fica em pastas chamadas training, então nunca sobrescreve um modelo existente. Pause as execuções agendadas do Prefect antes de começar (passo 1.1), para que nada execute enquanto você edita. Um alerta, repetido no passo 9: use dbt run -s <model name> e não coloque um + antes do nome quando seus modelos passarem a depender de modelos de produção, porque o + também reconstrói os modelos de produção de que eles dependem.

Como cada passo é organizado

Cada passo tem as mesmas quatro partes, para que você sempre saiba o que fazer em seguida.

  1. Por quê: uma ou duas frases sobre o que o passo ensina.

  2. No VS Code: o arquivo a criar ou editar, com o texto exato a colar. Quando um passo disser para substituir o arquivo, pressione Ctrl+A para selecionar tudo, cole por cima e pressione Ctrl+S. Nunca adicione código novo abaixo do código antigo.

  3. No terminal: os comandos a executar, cada um explicado.

  4. Verificação: o que você deve ver. Se não vir, pare e consulte a seção Solução de problemas antes de continuar.

A regra de ouro deste guia: mude uma coisa, execute, olhe o resultado. Nunca mude três coisas e só então execute. Quando algo quebrar, você saberá exatamente qual mudança causou o problema.

0.5 Como ler a saída do dbt

Todo comando dbt imprime muitas linhas. Você só precisa ler três coisas.

  • A linha do modelo. Por exemplo OK created sql external model staging.training_stg_population_values. OK significa que esse modelo foi construído.

1.4 Verificar o salt

O staging armazenará depois o usuário de entrada de dados como um hash, um valor embaralhado que não pode ser transformado de volta no nome. O embaralhamento precisa de um ingrediente secreto chamado salt, que fica na variável de ambiente HMIS_HASH_SALT. No terminal, em dbt/lake, execute:

echo ${HMIS_HASH_SALT:+salt is set}

O que significa: echo imprime texto. A parte de aparência estranha imprime salt is set somente se a variável tiver valor, e não imprime nada se estiver vazia. Ela nunca mostra o próprio segredo.

Se não imprimir nada, carregue-o a partir do arquivo .env do projeto:

export HMIS_HASH_SALT=$(grep '^HMIS_HASH_SALT=' ../../.env | cut -d= -f2-)

O que significa: grep encontra a linha que começa com HMIS_HASH_SALT= no arquivo .env duas pastas acima, cut mantém apenas a parte depois do sinal de igual, e export a guarda no seu terminal para esta sessão. Se você abrir um novo terminal mais tarde, precisará executá-lo de novo.

Nunca digite um valor como <the class salt> com os sinais de menor e maior: eles são um marcador de posição, não um valor real.

1.6 Criar um pequeno auxiliar para ver os resultados

Depois de cada passo você vai querer olhar as primeiras linhas de um modelo. O dbt tem um comando para isso, mas ele é longo, então você vai salvá-lo como um pequeno script.

  1. Em dbt/lake, crie uma pasta chamada hica_steps.

  2. Dentro dela, crie um arquivo chamado look.sh com este conteúdo e depois salve:

model="$1"; n="${2:-10}"; cols="${3:-*}"
dbt show --inline "select ${cols} from {{ ref('${model}') }}" --limit "${n}"

O que significa: o script aceita até três palavras depois do seu nome. A primeira é o nome do modelo, a segunda é quantas linhas mostrar (10 se você omitir) e a terceira são as colunas (todas, se você omitir). Em seguida ele executa dbt show --inline, que roda um select rápido e imprime uma prévia sem construir nada.

Você o usará assim, a partir de dbt/lake:

Passo 4: Preencher as lacunas

Por quê: o DHIS2 às vezes escreve orgUnit e period uma única vez no payload inteiro, em vez de em cada valor. Então o campo próprio do valor fica vazio (NULL).

No VS Code: substitua o arquivo inteiro. Clique dentro de training_stg_population_values.sql, pressione Ctrl+A para selecionar tudo, cole o código abaixo para que ele sobrescreva o antigo e pressione Ctrl+S. Não o adicione abaixo do código antigo e não crie um novo arquivo.

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

)

    dv.dataElement                           as data_element_id,

O que significa: coalesce(a, b) retorna a, ou b se a estiver vazio. Assim, cada valor usa sua própria unidade organizacional, se tiver uma, e a do payload inteiro caso contrário.

Passo 5: Transformar o valor em número

Por quê: value_raw é texto, e não se pode somar texto. Adicionamos uma versão numérica. Também mudamos a forma de armazenar o modelo, de view para tabela.

No VS Code: substitua o arquivo inteiro. Clique dentro de training_stg_population_values.sql, pressione Ctrl+A para selecionar tudo, cole o código abaixo para que ele sobrescreva o antigo e pressione Ctrl+S. Não o adicione abaixo do código antigo e não crie um novo arquivo.

{{ config(materialized='table') }}

with unnested as (

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

)

select
    dv.dataElement                           as data_element_id,
    dv.categoryOptionCombo                   as category_option_combo_id,
    coalesce(dv.orgUnit, payload_org_unit)   as org_unit_id,
    coalesce(dv.period, payload_period)      as period,
    dv.value                                 as value_raw,
    try_cast(dv.value as double)             as value_numeric
from unnested

O que significa: try_cast(x as double) converte texto em número decimal e devolve um valor vazio, em vez de falhar, quando o texto não é um número, por exemplo “n/a”. As duas linhas value_raw e value_numeric mantêm lado a lado o valor original e o convertido, então nada se perde.

Uma view apenas guarda a pergunta e a refaz toda vez. Uma tabela armazena a resposta, então os modelos seguintes a leem rapidamente.

A última consulta conta os textos que não puderam virar números. Verificação: a linha do log agora diz table model. Nos dados de referência a contagem foi 0, o que significa que todo valor era um número limpo.

Por quê: o período 2026 é apenas texto. Queremos saber seu tipo (anual, mensal, semanal) e sua data de início. O projeto já contém macros, pedaços reutilizáveis de SQL que alguém escreveu uma vez. Você as chama pelo nome entre chaves duplas.

No VS Code: substitua o arquivo inteiro. Clique dentro de training_stg_population_values.sql, pressione Ctrl+A para selecionar tudo, cole o código abaixo para que ele sobrescreva o antigo e pressione Ctrl+S. Não o adicione abaixo do código antigo e não crie um novo arquivo.

{{ config(materialized='table') }}

with unnested as (

    select
        orgUnit                as payload_org_unit,
        period                 as payload_period,
        unnest(dataValues)     as dv
    from {{ source('landing', 'data_values') }}
    where dataset = 'population'

),

restored as (

    select
        dv.dataElement                           as data_element_id,

O que significa: o arquivo agora tem três CTEs em sequência: unnested, restored, typed. Passo 7: Olhar antes de corrigir (encontrar duplicados)

Por quê: a pasta landing guarda todas as execuções de carga. Se um valor foi carregado duas vezes, ou corrigido depois, ele aparece mais de uma vez. Um engenheiro cuidadoso procura o problema antes de corrigi-lo. Nada nos seus arquivos muda neste passo.

dbt show --inline "select data_element_id, org_unit_id, period, category_option_combo_id, count(*) as copies from {{ ref('training_stg_population_values') }} group by all having count(*) > 1" --limit 10

O que significa: um valor é identificado por quatro coisas: o indicador, a unidade organizacional, o período e a combinação de categorias. group by all agrupa as linhas por essas quatro colunas. having count(*) > 1 mantém apenas os grupos que aparecem mais de uma vez. --limit 10 imprime no máximo 10 linhas.

Depois conte o quadro completo:

Leia o resultado com honestidade. Se rows_total for maior que distinct_values, a diferença é o número de cópias extras. Nos dados de referência eram 25.800 linhas para 10.320 valores distintos, então cada valor existia mais de uma vez. Se os dois números forem iguais nos seus dados, não há duplicados hoje, e o passo 8 não mudará sua contagem de linhas. Ainda vale a pena fazê-lo, porque uma carga futura pode trazer duplicados.

Passo 8: Manter apenas a cópia mais recente

Por quê: qual cópia manter? A mais recente. Classificamos as cópias de cada valor da mais nova para a mais antiga e mantemos a número um. Também deixamos de armazenar o modelo como tabela e o transformamos em um arquivo no Silo.

O que significa: row_number() over (partition by ... order by ...) dá um número às linhas dentro de cada grupo. Passo 10: Juntar os nomes dos indicadores

Por quê: uma junção (join) procura cada código em outra tabela e traz de volta o nome que pertence a ele. Aqui procuramos cada data_element_id em stg_dhis2__data_elements, um modelo que seu pipeline de produção já construiu.

No VS Code: substitua o arquivo inteiro. Clique dentro do arquivo, pressione Ctrl+A para selecionar tudo, cole o código abaixo para que ele sobrescreva o antigo e pressione Ctrl+S. Não o adicione abaixo do código antigo e não crie um novo arquivo.

select
    p.year,
    p.org_unit_id,
    de.data_element_name,
    p.value_numeric
from {{ ref('training_stg_population_values') }} as p
left join {{ ref('stg_dhis2__data_elements') }} as de
    on de.data_element_id = p.data_element_id

O que significa:

  • as p e as de são apelidos curtos para as duas tabelas, para que você possa escrever p.year e de.data_element_name.

  • left join (junção à esquerda) mantém todas as linhas da tabela da esquerda (seus valores de população), mesmo quando nenhum nome é encontrado. Nesse caso o nome fica vazio. Um join comum descartaria essas linhas silenciosamente, o que é perigoso.

  • on de.data_element_id = p.data_element_id diz como as duas tabelas se correspondem: os códigos devem ser iguais.

Passo 13: Sua primeira tabela gold

Por quê: gold é a tabela que um painel lê. A view dá uma linha por valor. Agora somamos os valores por distrito, ano e indicador, e o ClickHouse armazena o resultado.

No VS Code: crie a pasta gold no lugar certo. Clique com o botão direito na pasta training (a que fica diretamente sob models, ao lado de lake), escolha New Folder e digite gold. select
    toYear(ifNull(period_start_date, toDate32('1970-01-01')))  as year,
    ifNull(district_name, '')                                  as district_name,
    data_element_name,
    sum(value_numeric)                                         as value

O que cada parte significa:

  • ref('training_lake_population') aponta para sua view do ClickHouse, então o dbt constrói a view primeiro e a tabela depois.

  • group by mais sum() reduz muitas linhas a uma linha para cada distrito, ano e indicador, e soma seus valores.

  • Este modelo é uma tabela, e não uma view, porque as configurações de gold que você adicionou assim determinam. O resultado é armazenado, então os painéis o leem rapidamente e não leem o arquivo Parquet toda vez.

Parte 5: Testar seus modelos, passo 15

Um pipeline que executa não é o mesmo que um pipeline correto. Os testes são pequenas verificações automáticas que rodam sobre seus dados toda vez. Se os dados violarem uma regra, o teste avisa antes que um número errado chegue a um painel.

O dbt tem dois tipos de testes:

TipoOnde você o escreveComo funciona
Teste genéricoEm um arquivo .yml ao lado dos seus modelosVocê anexa uma regra pronta a uma coluna, como not_null (sem valores vazios) ou accepted_values (somente valores permitidos).
Teste singularUm arquivo .sql na pasta testsVocê escreve uma consulta que retorna as linhas ruins. Se não retornar nada, o teste passa.

O resultado de um teste é PASS, WARN (uma regra foi violada, mas marcada como aviso) ou FAIL (uma regra foi violada e marcada como erro).

Passo 15a: Testes genéricos para os modelos lake

No VS Code, em dbt/lake/models/training, crie um arquivo chamado _training__models.yml. Ele fica diretamente dentro de training, ao lado das pastas staging e intermediate. Cole e salve:

version: 2

models:
  - name: training_stg_population_values
    columns:
      - name: data_element_id
        data_tests: [not_null]
      - name: org_unit_id
        data_tests: [not_null]
      - name: period_type
        data_tests:
          - accepted_values:
              arguments: {values: ['Yearly']}
              config: {severity: warn}
      - name: value_numeric
        data_tests:
          - not_null:
              config: {severity: warn}

  - name: training_int_population_by_district
    columns:
      - name: data_element_name
        data_tests: [not_null]
      - name: district_name
        data_tests:
          - not_null:
              config: {severity: warn}

O que significa: cada - name: sob models é um modelo, e cada - name: sob columns é uma de suas colunas. data_tests lista as regras dessa coluna. As regras marcadas com severity: warn relatam um problema sem interromper nada. Por exemplo, um valor não numérico vale a pena conhecer, mas não é um desastre.

with production as (
    select
        toYear(ifNull(period_start_date, toDate32('1970-01-01')))   as year,
        ifNull(district_name, '')                                   as district_name,
        sumIf(value_numeric, data_element_name = 'Total population < 1 year') as under1_population
    from {{ ref('lake_dhis2__data_values') }}
    where data_set_name = 'Population' and period_type = 'Yearly'
    group by year, district_name
)
select t.year, t.district_name, t.under1_population, p.under1_population as production_value
from {{ ref('training_fct_population_district_year') }} as t
inner join production as p on p.year = t.year and p.district_name = t.district_name
where abs(t.under1_population - p.under1_population) > 0.5

O que significa: este é o teste mais valioso do guia. Ele calcula o mesmo número a partir do pipeline de produção e o compara com sua tabela de treinamento. Quando você terminar

  • Retome o pipeline em produção. Abra o Prefect, vá em Work Pools, abra hmis-process-pool e ligue-o de novo.

  • Os modelos de treinamento podem ficar. Eles são pequenos, e o dbt build agendado simplesmente os construirá também. Se o projeto precisar ficar limpo, exclua-os da construção agendada.

  • Guarde seus backups (dbt_project.yml.bak nos dois projetos) até terminar o guia inteiro; depois você pode apagá-los.

  • Tente de novo com outro conjunto de dados. Os mesmos oito movimentos funcionam para qualquer conjunto de dados do DHIS2: lê-lo, desagrupá-lo, nomear as colunas, preencher as lacunas, tipar os valores, remover duplicados, adicionar nomes e depois resumi-lo para um painel.

From DHIS2 to dashboards: how the HMIS data platform works

Every night this project copies health data out of DHIS2, lands it untouched in a data lake, cleans and joins it with dbt, builds reporting tables in ClickHouse, and shows them in Metabase. This guide explains every step, every function and every file, and shows how to create and run your own Prefect deployment or dbt model.

The big picture

Picture a town’s water system. DHIS2 is the spring. The landing area is an intake tank that keeps the water exactly as it arrived, labelled with the day it came in. Staging and intermediate are the treatment plant, where dbt filters, standardises and blends the data. The gold marts are the taps, and Metabase is where people fill their glasses. Prefect is the control room: it opens the valves on time, notices when a pump fails, and stops the plant before dirty water reaches a tap.

Three rules the design follows

Land first, change later. Ingestion never transforms anything. It stores each DHIS2 answer as received, so you can always replay history. All cleaning happens in dbt.

Stop at the first failure. Ingestion, then dbt lake, then dbt warehouse. If a step fails, the later ones do not run, so gold is never rebuilt from bad data. Dashboards keep showing the last good run and the team gets an e-mail.

Personal data stops early. DHIS2 values carry the name of the person who entered them and a free-text comment. Staging hashes the name, intermediate removes both, and ClickHouse and Metabase never see them.

Why gold lives only in ClickHouse

Silo keeps the detailed, reusable data (down to intermediate) as cheap files any engine can read. Gold is a set of aggregates that ClickHouse builds from it in seconds, so a second copy in the lake would only have to be kept in sync. If ClickHouse is lost, running dbt build in dbt/warehouse recreates gold from Silo.

Words you will meet

Most beginner confusion is vocabulary. Skim this list now and come back when a word trips you up.

Orchestration

Flow
A Python function marked @flow. Prefect tracks every run. A flow can call other flows (subflows).
Task
A smaller function marked @task, called from a flow. A task can retry by itself when it fails.
Run
One execution of a flow, with its own page and logs in the Prefect UI.
Deployment
A saved instruction: “run this flow, with these parameters, on this schedule.” Defined in prefect.yaml.
Parameters
The inputs of a flow, such as mode or datasets. A deployment fixes them; you can override them per run.
Schedule
A cron expression plus a timezone that tells Prefect when to start a deployment.
Work pool and worker
The pool is a queue of runs waiting to happen. The worker is a program you keep running that picks runs up and executes them.
Watermark
A bookmark: the DHIS2 server time of the last successful run. The next incremental run asks only for values changed since then.
Manifest
A small JSON receipt written at the end of each run: what landed, what failed.
run_id
A timestamp like 20261104T000000Z that labels everything one run wrote.

Storage

Data lake
A bucket of files, cheap and readable by any engine. Here it is Silo, a maintained fork of MinIO with the same S3 API.
Bucket and prefix
The bucket is the top-level folder (hmis-datalake). A prefix is a path inside it, such as landing/dhis2/.
Landing, staging, intermediate, gold
The layers (sometimes called medallion layers). Each is cleaner and more refined than the one before.
Parquet
A compact, typed, column-oriented file format that DuckDB and ClickHouse read quickly.
Hive-style partition
Folders named key=value, such as run_id=…/mode=full/. DuckDB turns them into columns.
ClickHouse
A fast analytical database. It holds only the gold marts.
DuckDB
A small analytical engine that runs inside the dbt process. It reads and writes Parquet in Silo.

Transformation

dbt
A tool that turns SQL SELECT files into tables or files, in the right order, and tests them.
Model
One .sql file containing one SELECT. dbt builds it into a table, view or file.
Source
Data dbt reads but does not build. Here, the landing files.
ref() and source()
Jinja functions that point at another model or source. They tell dbt the build order.
Materialization
How a model is stored: external (a Parquet file), view, or table.
Test
A rule checked after a model is built. A failing test stops the pipeline; a warning is only logged.
Macro
A reusable Jinja function, such as hash_pii(). Lives in macros/.
Mart
A finished table for reporting. “Fact” tables hold measures; a “dimension” describes things like org units.
Grain
What one row stands for, such as “one district, one month, one data element.”
Surrogate key
A made-up unique id, here an md5 hash of the natural key columns.

Privacy and access

PII
Personal data. Here: storedBy (who entered a value) and comment (free text).
Hash and salt
A hash turns a name into an unreadable code. The salt is a secret added first, so nobody can reverse the code by guessing names.
Named collection
A ClickHouse setting that stores the lake’s address and keys, so SQL can say s3(silo, …) without a password.
Environment variable
A named setting outside the code, such as MINIO_ENDPOINT. Secrets live in .env.
YAML
A text format for settings. Indentation matters: two spaces mean “this belongs to the line above.”
Metabase
The dashboard tool that queries gold.

Two more things run on the host, outside Docker: the Prefect worker (it needs your code, DHIS2 access and dbt) and dbt itself, each in its own virtual environment so their packages never clash. Change every local password before using this anywhere but a laptop.

What setup.sh does

  1. Checks the prerequisites

    Docker running, the Compose plugin, curl, and Python 3.10 or newer with venv. It warns if the repository sits on the Windows drive (/mnt/c/…), because files there are slow.

  2. Prepares .env

    Copies .env.example to .env and fills in a fresh random HMIS_HASH_SALT, the path of DBT_EXECUTABLE and HMIS_PROJECT_DIR. It locks the file (chmod 600) and creates ~/hmis-data for the DuckDB file. Existing values are never overwritten.

  3. Creates two virtual environments

    ~/venvs/hmis-ingestion for Prefect and the pipeline, ~/venvs/hmis-dbt for dbt-core, dbt-duckdb and dbt-clickhouse. Keeping them apart stops dependency clashes.

  4. Starts the containers

    Runs docker compose up -d and waits until Silo, ClickHouse and Prefect answer their health checks.

  5. Registers the Prefect deployments

    Creates the hmis profile, the work pool hmis-process-pool, then runs prefect deploy --all.

  6. Loads data once

    Runs the whole pipeline in full mode for 12 months (or --months N): ingestion, dbt lake, dbt warehouse, docs. Takes roughly 5 to 15 minutes. Skipped with --skip-data.

  7. Builds the Metabase dashboard

    Runs metabase/setup_metabase.py. Also skipped with --skip-data.

It is safe to run again: finished steps are skipped. Afterwards, start the worker and keep its terminal open:

./start_worker.sh

ingestion: how much to pull

ingestion:
  mode: incremental
  lookback_months: 12

incremental fetches only values changed since the last good run. full re-pulls the last lookback_months months. These are defaults; a deployment’s parameters can override them.

  chunk_months: 1
  overlap_days: 7

A full load is cut into one request per calendar month. Each window starts 7 days early because DHIS2 only returns periods that fall wholly inside the window, so a weekly period that straddles a month boundary would otherwise be lost.

The toolbox: hmis.py

hmis.py holds the building blocks the flows call. It has no Prefect code in it, so you can import it from a notebook or a test and use it on its own. Read it as five small tools: a config loader, a DHIS2 client, a data lake client, a dbt runner and an e-mail sender, plus two helpers.

load_config(path)configReads the YAML file and fills in the ${VAR:-default} patterns. 
load_dotenv(path.parent / ".env")

If python-dotenv is installed, first read the .env file next to the config into the environment. This is why secrets never need to be in the YAML. If the package is missing, this step is skipped.

return _expand_env(yaml.safe_load(fh))

Parse the YAML into dictionaries and lists, then walk through all of them replacing ${VAR} and ${VAR:-default}.

_expand_env is the walker. It works recursively on dictionaries, lists and strings. If a variable is not set and has no default, it raises KeyError instead of quietly using an empty value. as_bool turns text such as "true", "1", "yes" or "on" into a real True, because environment variables are always text.

DHIS2ClientclassA small, retrying client for the DHIS2 Web API.
  • __init__ opens one HTTP session with the login and a retry rule: up to max_retries times, with growing pauses, when DHIS2 answers 429, 500, 502, 503 or 504 (busy or broken). Only read requests (GET) are retried. This is a first safety net below Prefect’s own task retries.
  • from_config(source_cfg) builds a client from the source block of the config.
  • get(endpoint, params) calls /api/<endpoint>, raises an error on a bad status, and returns the parsed JSON.
  • server_time() reads system/info and returns serverDate. The pipeline uses it as the watermark so it never depends on your laptop’s clock.
  • iter_metadata(resource, fields, filters) yields every object of a metadata list. It asks for page after page (page_size at a time) until the pager says there are no more.
  • get_data_values(...) calls dataValueSets.json with the data set, the org unit, children=true and either a date window (startDate, endDate) or lastUpdated. It returns the payload untouched. DHIS2 sometimes moves fields shared by every value (like attributeOptionCombo) to the top of the payload; dbt staging puts them back.
DataLakeclassA wrapper around the MinIO client that works with Silo or any S3 store.
  • from_config(lake_cfg) builds it from the datalake block.
  • uri(key) returns s3://bucket/key, used in log lines.
  • ensure_bucket() creates the bucket if it does not exist.
  • put_bytes, get_bytes, exists, list_keys are the primitives: write an object, read it, check that it is there, list keys under a prefix.
  • put_json(key, obj) turns Python data into JSON text and uploads it. If the key ends in .gz it gzips it first. get_json does the reverse.
  • read_state(key) returns the saved dictionary or None if there is no file yet (a first run). write_state saves it. Together they keep the watermark.
date_windows(end, lookback_months, chunk_months, overlap_days)helperCuts a lookback period into calendar-aligned request windows. 
end_idx = end.year * 12 + end.month - 1
idx = end_idx - lookback_months + 1
idx -= idx % chunk_months

Counts months as one running number. Step back lookback_months, then round down to a multiple of the chunk size. With chunks of 3 this lands on January, April, July or October; with 12 on January.

start = date(idx // 12, idx % 12 + 1, 1) - timedelta(days=overlap_days)
stop  = date(nxt // 12, nxt % 12 + 1, 1) - timedelta(days=1)

Each window starts on the first day of its first month minus the overlap, and ends on the last day of its last month. The overlap exists because DHIS2 only returns periods that fall entirely inside the window, so a week that straddles two months would otherwise be lost. The duplicates this creates are removed in dbt staging.

The folder this file lives in, and the default config name. Anchoring on the file’s own folder means the pipeline works no matter which directory you start it from.

Every function, one by one

Open any card for a plain-language explanation. Tasks have retry settings, which are in the card headers because they matter when something fails.

_resolve_config(config_path)helperTurns a relative config path into an absolute one.

What one run does

Here is a nightly run from the clock striking 02:00 to the last log line.

  1. Prefect starts the flow

    The cron 0 2 * * * in Kigali time fires. A worker picks the run from the pool and loads dataset_ingestion.py from the project folder. 02:00 in Kigali is 00:00 UTC, so the run id begins with the UTC time, for example 20261104T000000Z.

  2. Setup

    prepare_lake confirms the bucket. get_server_time fetches the watermark. Four ingest_metadata tasks land the dictionaries in parallel.

  3. Each data set, one at a time

    plan_requests chooses the calls. extract_data_values makes them (up to 4 at a time) and lands each response. update_watermark moves the bookmark.

  4. Receipt and gate

    write_manifest saves the run summary. If any data set failed, the flow raises here and the run stops.

  5. dbt lake, then dbt warehouse

    Landing becomes staging and intermediate Parquet in Silo, then gold marts in ClickHouse. A failing test stops the run before gold is touched. The dbt sections below explain each step.

  6. Docs and finish

    dbt docs are refreshed. If anything failed or crashed earlier, notify_failure has already emailed the team.

  when column is null or trim(column) = '' then null

    id: AbCdEfGhIjK             # the DHIS2 data set ID

Run dbt on its own: a dbt-only deployment

  
Today every deployment runs hmis_pipeline, which always ingests first. The with_dbt=false switch skips dbt, but there is no switch that skips ingestion. If you have just edited a dbt model and want to rebuild without calling DHIS2 again, you have two choices.


  
Option 1: run dbt by hand

  
No Prefect needed. dbt needs the secrets from .env in its environment, so export them first:

  
source ~/venvs/hmis-dbt/bin/activate
cd ~/hmis_ingestion
set -a; . ./.env; set +a          # HMIS_HASH_SALT, MINIO_*, CLICKHOUSE_*, HMIS_DUCKDB_PATH

cd dbt/lake      && dbt debug && dbt build     # landing -> staging -> intermediate
cd ../warehouse  && dbt debug && dbt build     # intermediate -> gold

  
dbt debug checks the profile and the connection before you build. Run the lake project first: the warehouse reads the files it writes.


  
Option 2: add a small flow and deploy it

  

    
A suggestion, not part of the repository. The code below reuses the existing dbt_build and dbt_docs tasks. I have not run it, so test it before relying on it.

  

  
Add this to the end of dataset_ingestion.py, above the _parse_args function:

  
@flow(
    name="hmis-dbt-only",
    log_prints=True,
    on_failure=[notify_failure],
    on_crashed=[notify_failure],
)
def hmis_dbt_only(config_path: str = DEFAULT_CONFIG) -> dict:
    """Rebuild lake then warehouse from what is already in landing."""
    config_path = _resolve_config(config_path)
    result = {}
    for project in ("lake", "warehouse"):
        result[project] = dbt_build(config_path, project)
    return result

  
Then add a deployment to prefect.yaml and register it:

  
  - name: hmis-dbt-only
    description: Rebuild dbt lake and warehouse from existing landing data; no ingestion.
    entrypoint: dataset_ingestion.py:hmis_dbt_only
    tags: *tags
    parameters:
      config_path: ingestion_config.yml
    work_pool: *hmis_pool
    concurrency_limit: 1

  
prefect deploy --name hmis-dbt-only
prefect deployment run "hmis-dbt-only/hmis-dbt-only"

  
Note the run name: it is flow-name/deployment-name, and here the flow is hmis-dbt-only. The failure e-mail hook works unchanged, because it only needs the flow’s config_path parameter.

    Write the model
    
      
    Create dbt/warehouse/models/gold/fct_measles_by_chiefdom_monthly.sql. Read from a lake view with ref(), wrap key columns in ifNull(), and set the sort key.

-- Measles doses given per chiefdom and month (Child Health, monthly).
-- Grain: month x district x chiefdom.

select
    toDate(ifNull(period_start_date, toDate32('1970-01-01'))) as month,
    ifNull(district_name, '')   as district_name,
    ifNull(chiefdom_name, '')   as chiefdom_name,
    sum(value_numeric)          as measles_doses,
    uniqExact(org_unit_id)      as facilities_reporting
from {{ ref('lake_dhis2__data_values') }}
where data_set_period_type = 'Monthly'
  and is_expected_period_type
  and data_element_name = 'Measles doses given'
group by month, district_name, chiefdom_name

When something goes wrong

  
Start at the Prefect UI: open the run, read the red log line, and match it below. Check the e-mail inbox at localhost:8025 too: failed runs send a message with the reason and a link.

  

    
What you seeLikely causeWhat to do

    
      
A web page (Silo, ClickHouse, Prefect, Metabase, docs, Mailpit) does not loadUbuntu shut down, taking Docker with it.Open an Ubuntu terminal; the containers start within seconds. Check with docker compose ps.

      
No scheduled runs happen; runs stay Scheduled, Pending or LateThe worker is not running, or the pool name differs.Start ./start_worker.sh. In Prefect, Work Pools, hmis-process-pool should show Online.

      
New deployment is not in the UIThe file was saved but never registered, or the CLI points at another Prefect server.Run prefect deploy --name .... Check prefect profile ls shows hmis as active.

      
Run crashes before any task: file or directory not foundHMIS_PROJECT_DIR is not set where the worker runs.Start the worker with ./start_worker.sh, which sets it.

      
ModuleNotFoundError: hmisThe worker was started outside the ingestion virtual environment.Use ./start_worker.sh, which uses ~/venvs/hmis-ingestion.

      
Run fails at once with a parameter errorA misspelled parameter name, or the wrong type (for example datasets as text instead of a list).Compare with the five parameters. Lists need one dash per item.

      
Dataset 'x' not found in configThe value in datasets is not a key from the config (often the DHIS2 id).Use the short key, such as child_health.

      
DHIS2 returns 404 or is very slowThe play server rotates versions and is shared.Pick a current instance at play.dhis2.org and set DHIS2_BASE_URL in .env.

      
dbt fails with “HMIS_HASH_SALT must be set”The salt is missing from .env, or .env was not exported when running dbt by hand.Add the salt; run set -a; . ./.env; set +a before dbt.

      
dbt step fails with command not foundDBT_EXECUTABLE is not the dbt in its own virtual environment.Set the full path in .env (setup.sh does this).

      
A dbt test fails and the run stopsThe data broke a rule. Gold was not rebuilt, so dashboards show the last good run.Read the dbt lines in the Prefect log. Run the test’s SQL to see the bad rows. Fix the data or the model, then run again.

      
Ingestion worked but dashboards did not changeThe run had with_dbt: false, or an earlier step failed.Check the run’s parameters and look for the dbt lines in the log.

      
“Port already in use” when starting DockerAnother stack owns the default ports.This stack already uses 9100, 9101, 8124, 9010, 4200, 3010, 8085, 8025 and 1025 for that reason. Stop whatever holds the port.

      
No HMIS Overview dashboard in MetabaseIt is built last by setup.sh, and skipped with --skip-data.Load data, then run python metabase/setup_metabase.py.

      
No failure e-mail arrivesSMTP settings are the local defaults.Look in Mailpit, or set the SMTP_* variables in .env.

    
  

  
One reassuring fact: landing files are never overwritten and the watermark only moves after success, so a failed run is safe to re-run. It will not lose data or double-count it; dbt de-duplicates.

De DHIS2 aux tableaux de bord : comment fonctionne la plateforme de données HMIS

  
Chaque nuit, ce projet copie les données de santé depuis DHIS2, les dépose telles quelles dans un data lake, les nettoie et les joint avec dbt, construit des tables de reporting dans ClickHouse et les affiche dans Metabase. Ce guide explique chaque étape, chaque fonction et chaque fichier, et montre comment créer et lancer votre propre déploiement Prefect ou modèle dbt.


  

    

      
DHIS2
Les établissements y saisissent leurs chiffres. Nous ne faisons que lire.

      
Landing
Copies exactes de ce que DHIS2 a envoyé, gardées dans Silo.

      
Staging et intermediate
dbt nettoie, joint et retire les données personnelles.

      
Marts gold
Tables ClickHouse prêtes pour le reporting.

Metabase lit gold, en lecture seule.

4 Metabase interroge gold

    

  







  
Vue d’ensemble

  
Imaginez le réseau d’eau d’une ville. DHIS2 est la source. La zone landing est un réservoir d’arrivée qui garde l’eau telle qu’elle est arrivée, étiquetée avec le jour de sa réception. Staging et intermediate forment la station de traitement, où dbt filtre, standardise et assemble les données. Les marts gold sont les robinets, et Metabase est l’endroit où l’on remplit son verre. Prefect est la salle de contrôle : il ouvre les vannes à l’heure, repère une pompe en panne et arrête la station avant que de l’eau sale n’atteigne un robinet.


  
Trois règles de conception

  
Déposer d’abord, modifier ensuite. L’ingestion ne transforme jamais rien. Elle stocke chaque réponse de DHIS2 telle quelle, ce qui permet de rejouer l’historique. Tout le nettoyage se fait dans dbt.

  
S’arrêter au premier échec. Ingestion, puis dbt lake, puis dbt warehouse. Si une étape échoue, les suivantes ne s’exécutent pas : gold n’est donc jamais reconstruit à partir de données défectueuses. Les tableaux de bord continuent d’afficher la dernière bonne exécution et l’équipe reçoit un e-mail.

  
Les données personnelles s’arrêtent tôt. Les valeurs DHIS2 portent le nom de la personne qui les a saisies et un commentaire libre. Staging hache le nom, intermediate retire les deux, et ClickHouse comme Metabase ne les voient jamais.

Pourquoi gold n’existe que dans ClickHouse

  
Silo conserve les données détaillées et réutilisables (jusqu’à intermediate) sous forme de fichiers peu coûteux que n’importe quel moteur peut lire. Le vocabulaire

  
Une bonne part de la confusion des débutants vient du vocabulaire. Parcourez cette liste maintenant et revenez-y dès qu’un mot vous arrête.

  
Orchestration

  

    
Flow
Une fonction Python marquée @flow. Prefect suit chaque exécution. Un flow peut en appeler d’autres (sous-flows).

    
Tâche (task)
Une fonction plus petite, marquée @task et appelée depuis un flow. Une tâche peut se relancer seule en cas d’échec.

    
Exécution (run)
Un lancement d’un flow, avec sa propre page et ses journaux dans l’interface Prefect.

    
Déploiement
Une consigne enregistrée : « lance ce flow, avec ces paramètres, selon cette planification ». Défini dans prefect.yaml.

    
Paramètres
Les entrées d’un flow, comme mode ou datasets. Un déploiement les fixe ; vous pouvez les remplacer à chaque exécution.

    
Planification (schedule)
Une expression cron et un fuseau horaire qui disent à Prefect quand démarrer un déploiement.

    
Pool de travail et worker
Le pool est une file d’exécutions en attente. Le worker est un programme que vous laissez tourner : il prend les exécutions et les réalise.

    
Watermark
Un signet : l’heure du serveur DHIS2 lors de la dernière exécution réussie. La prochaine exécution incrémentale ne demande que les valeurs modifiées depuis.

    
Manifeste
Un petit reçu JSON écrit à la fin de chaque exécution : ce qui a été déposé, ce qui a échoué.

    
run_id
Un horodatage comme 20261104T000000Z qui étiquette tout ce qu’une exécution a écrit.

  

  
Stockage

  

    
Data lake
Un bucket de fichiers, peu coûteux et lisible par n’importe quel moteur. Ici, c’est Silo, un fork maintenu de MinIO avec la même API S3.

    
Bucket et préfixe
Le bucket est le dossier de plus haut niveau (hmis-datalake). Un préfixe est un chemin à l’intérieur, comme landing/dhis2/.

    
Landing, staging, intermediate, gold
Les couches (parfois appelées couches médaillon). Chacune est plus propre et plus élaborée que la précédente.

    
Parquet
Un format de fichier compact, typé et orienté colonnes, que DuckDB et ClickHouse lisent vite.

    
Partition de style Hive
Des dossiers nommés clé=valeur, comme run_id=…/mode=full/. DuckDB les transforme en colonnes.

    
ClickHouse
Une base de données analytique rapide. Elle ne contient que les marts gold.

    
DuckDB
Un petit moteur analytique qui tourne dans le processus dbt. Il lit et écrit du Parquet dans Silo.

  

  
Transformation

  

    
dbt
Un outil qui transforme des fichiers SQL SELECT en tables ou en fichiers, dans le bon ordre, et les teste.

    
Modèle
Un fichier .sql contenant un SELECT. dbt le construit en table, vue ou fichier.

    
Source
Des données que dbt lit mais ne construit pas. Ici, les fichiers landing.

    
ref() et source()
Des fonctions Jinja qui pointent vers un autre modèle ou une source. Elles indiquent à dbt l’ordre de construction.

    
Matérialisation
La façon dont un modèle est stocké : external (un fichier Parquet), view ou table.

    
Test
Une règle vérifiée après la construction d’un modèle. Un test en échec arrête le pipeline ; un avertissement est seulement journalisé.

    
Macro
Une fonction Jinja réutilisable, comme hash_pii(). Se trouve dans macros/.

    
Mart
Une table finie pour le reporting. Les tables de « faits » contiennent des mesures ; une « dimension » décrit des objets comme les unités d’organisation.

    
Granularité (grain)
Ce que représente une ligne, par exemple « un district, un mois, un élément de données ».

    
Clé de substitution
Un identifiant unique fabriqué, ici un hash md5 des colonnes de la clé naturelle.

  

  
Confidentialité et accès

  

    
PII
Données personnelles. Ici : storedBy (qui a saisi une valeur) et comment (texte libre).

    
Hash et sel
Un hash transforme un nom en code illisible. Le sel est un secret ajouté au préalable : personne ne peut remonter du code au nom en essayant des noms au hasard.

    
Named collection
Un réglage ClickHouse qui garde l’adresse et les clés du lake, pour que le SQL puisse écrire s3(silo, …) sans mot de passe.

    
Variable d’environnement
Un réglage nommé hors du code, comme MINIO_ENDPOINT. Les secrets vivent dans .env.

    
YAML

Installation et services

  
Tout tourne sur un seul portable, dans Ubuntu sous WSL (Windows), depuis le dossier du dépôt. Cloner ne fait que télécharger le code : lancez d’abord ./setup.sh une fois.

Ce que fait setup.sh

  
    
    
  1. Vérifie les prérequis
    Docker en marche, le plugin Compose, curl, et Python 3.10 ou plus récent avec venv. Il avertit si le dépôt est sur le disque Windows (/mnt/c/…), car les fichiers y sont lents.
    2. 
    
  2. Prépare .env
    Copie .env.example vers .env et renseigne un nouveau HMIS_HASH_SALT aléatoire, le chemin de DBT_EXECUTABLE et HMIS_PROJECT_DIR. Il verrouille le fichier (chmod 600) et crée ~/hmis-data pour le fichier DuckDB. Les valeurs existantes ne sont jamais écrasées.
    3. 
    
  3. Crée deux environnements virtuels
    ~/venvs/hmis-ingestion pour Prefect et le pipeline, ~/venvs/hmis-dbt pour dbt-core, dbt-duckdb et dbt-clickhouse. Les garder séparés évite les conflits de dépendances.
    4. 
    
  4. Démarre les conteneurs
    Lance docker compose up -d et attend que Silo, ClickHouse et Prefect répondent à leurs tests de santé.
    5. 
    
  5. Enregistre les déploiements Prefect
    Crée le profil hmis, le pool de travail hmis-process-pool, puis lance prefect deploy --all.
    6. 
    
  6. Charge les données une fois
    Exécute tout le pipeline en mode full sur 12 mois (ou --months N) : ingestion, dbt lake, dbt warehouse, docs. Compter 5 à 15 minutes environ. Ignoré avec --skip-data.
    7. 
    
  7. Construit le tableau de bord Metabase
    Lance metabase/setup_metabase.py. Également ignoré avec --skip-data.
    8. 
  

  
On peut le relancer sans risque : les étapes terminées sont ignorées. Ensuite, démarrez le worker et gardez son terminal ouvert :

Le fichier de configuration

  
ingestion_config.yml contient tous les réglages dont le code a besoin : changer de serveur ou ajouter un jeu de données n’oblige donc jamais à modifier le Python. Chaque bloc ci-dessous montre à gauche de vraies lignes du fichier et à droite leur signification.


  

    
Lire ${NOM:-défaut}. Le chargeur remplace ces motifs par des variables d’environnement. ${MINIO_BUCKET:-hmis-datalake} signifie « utilise la variable MINIO_BUCKET si elle existe, sinon utilise hmis-datalake ». C’est ainsi que le même fichier fonctionne sur un portable et sur un serveur, et que les vrais mots de passe restent hors du fichier.

  


  
source : d’où viennent les données

  

    
source:
  name: dhis2_demo
  system: dhis2
Une étiquette pour cette source. Le nom est écrit dans chaque manifeste d’exécution.

    
  base_url: ${DHIS2_BASE_URL:-https://play.im.dhis2.org/stable-2-43-2-1}
Le serveur DHIS2. La démo publique change de version régulièrement : si elle ne répond plus, choisissez une adresse actuelle sur play.dhis2.org et renseignez DHIS2_BASE_URL.

    
  username: ${DHIS2_USERNAME:-admin}
  password: ${DHIS2_PASSWORD:-district}
L’identifiant public de la démo. Pour un vrai serveur, renseignez-les dans .env.

    
  timeout_seconds: 180
  max_retries: 5
  page_size: 1000
Combien de temps attendre une réponse, combien de fois le client retente une requête, et combien d’enregistrements récupérer par page. Ces valeurs sont lues par DHIS2Client.

  


  
datalake : où vont les données

  

    
datalake:
  endpoint: ${MINIO_ENDPOINT:-localhost:9100}
  access_key: ${MINIO_ACCESS_KEY:-minioadmin}
  secret_key: ${MINIO_SECRET_KEY:-minioadmin}
  secure: ${MINIO_SECURE:-false}
L’adresse et l’identifiant de Silo. Le point d’accès est simplement hôte:port, sans http://. Mettez secure à true si le stockage est derrière TLS.

    
  bucket: ${MINIO_BUCKET:-hmis-datalake}
Le bucket est le dossier de plus haut niveau où tout vit. La première tâche de chaque exécution le crée s’il manque.

    
  landing_prefix: landing/dhis2
  state_prefix: _state/dhis2
  runs_prefix: _runs/dhis2
Trois dossiers dans le bucket : les données brutes, les watermarks et les manifestes d’exécution. dbt gère staging/ et intermediate/ ; l’ingestion n’y écrit jamais.

  


  
ingestion : quelle quantité récupérer

  

    
ingestion:
  mode: incremental
  lookback_months: 12
incremental ne récupère que les valeurs modifiées depuis la dernière bonne exécution. full recharge les lookback_months derniers mois. Ce sont des valeurs par défaut ; les paramètres d’un déploiement peuvent les remplacer.

    
  chunk_months: 1
  overlap_days: 7
Un chargement complet est découpé en une requête par mois civil. Chaque fenêtre commence 7 jours plus tôt, car DHIS2 ne renvoie que les périodes entièrement comprises dans la fenêtre : une période hebdomadaire à cheval sur deux mois serait sinon perdue.

Les « métadonnées » sont le dictionnaire qui explique les chiffres : noms des éléments de données, noms et hiérarchie des établissements, combinaisons de catégories, et établissements rattachés à chaque formulaire. Quatre de ces ressources sont enregistrées à chaque exécution, pour que dbt puisse joindre les noms aux valeurs. fields liste les colonnes à demander.

Défini mais désactivé. Il est ignoré, sauf si vous le nommez explicitement dans le paramètre datasets.

La boîte à outils : hmis.py

  
hmis.py contient les briques que les flows appellent. Il ne contient aucun code Prefect : on peut donc l’importer depuis un notebook ou un test et l’utiliser seul. Voyez-le comme cinq petits outils, un chargeur de configuration, un client DHIS2, un client du data lake, un lanceur dbt et un expéditeur d’e-mails, plus deux utilitaires.


  

  


    
load_config(path)configLit le fichier YAML et remplace les motifs ${VAR:-défaut}.
      

        

          
load_dotenv(path.parent / ".env")
Si python-dotenv est installé, lit d’abord le fichier .env situé à côté de la configuration et le charge dans l’environnement. C’est pourquoi les secrets n’ont jamais besoin d’être dans le YAML. Si le paquet manque, cette étape est ignorée.

          
return _expand_env(yaml.safe_load(fh))
Interprète le YAML en dictionnaires et listes, puis les parcourt tous en remplaçant ${VAR} et ${VAR:-défaut}.

        

        
_expand_env est ce parcours. Il travaille récursivement sur les dictionnaires, les listes et les chaînes. Si une variable n’est pas définie et n’a pas de valeur par défaut, il lève KeyError au lieu d’utiliser discrètement une valeur vide. as_bool transforme un texte comme "true", "1", "yes" ou "on" en vrai True, car les variables d’environnement sont toujours du texte.


    
DHIS2ClientclasseUn petit client à relances pour l’API Web de DHIS2.
      

        
    
          
  • __init__ ouvre une session HTTP avec l’identifiant et une règle de relance : jusqu’à max_retries fois, avec des pauses croissantes, quand DHIS2 répond 429, 500, 502, 503 ou 504 (occupé ou en panne). Seules les requêtes de lecture (GET) sont relancées. C’est un premier filet de sécurité sous les relances de tâche de Prefect.
    • 
          
  • from_config(source_cfg) construit un client à partir du bloc source de la configuration.
    • 
          
  • get(endpoint, params) appelle /api/<endpoint>, lève une erreur si le statut est mauvais et renvoie le JSON interprété.
    • 
          
  • server_time() lit system/info et renvoie serverDate. Le pipeline l’utilise comme watermark pour ne jamais dépendre de l’horloge de votre portable.
    • 
          
  • iter_metadata(resource, fields, filters) produit chaque objet d’une liste de métadonnées. Il demande page après page (page_size à la fois) jusqu’à ce que le pager indique qu’il n’y en a plus.
    • 
          
  • get_data_values(...) appelle dataValueSets.json avec le jeu de données, l’unité d’organisation, children=true et soit une fenêtre de dates (startDate, endDate), soit lastUpdated. Il renvoie la charge utile intacte. DHIS2 remonte parfois en tête de charge utile les champs communs à toutes les valeurs (comme attributeOptionCombo) ; le staging dbt les remet en place.

date_windows(end, lookback_months, chunk_months, overlap_days)utilitaireDécoupe une période de rétrospective en fenêtres de requête alignées sur le calendrier.
      

        

          
end_idx = end.year * 12 + end.month - 1
idx = end_idx - lookback_months + 1
idx -= idx % chunk_months
Compte les mois comme un seul nombre courant. Remonte de lookback_months, puis arrondit vers le bas à un multiple de la taille de découpage. Avec des blocs de 3, on tombe sur janvier, avril, juillet ou octobre ; avec 12, sur janvier.

          
start = date(idx // 12, idx % 12 + 1, 1) - timedelta(days=overlap_days)
stop  = date(nxt // 12, nxt % 12 + 1, 1) - timedelta(days=1)
Chaque fenêtre commence au premier jour de son premier mois moins le chevauchement, et finit au dernier jour de son dernier mois. Le chevauchement existe car DHIS2 ne renvoie que les périodes situées entièrement dans la fenêtre : une semaine à cheval sur deux mois serait sinon perdue. Les doublons ainsi créés sont retirés dans le staging dbt.

Le début du fichier

  

    
from prefect import flow, get_run_logger, task
from prefect.cache_policies import NO_CACHE
from prefect.task_runners import ThreadPoolTaskRunner
Les briques de Prefect. flow et task sont les décorateurs. get_run_logger écrit des lignes dans la page de journal de l’exécution. ThreadPoolTaskRunner permet à plusieurs tâches de tourner côte à côte.

    
from hmis import (DataLake, DbtError, DHIS2Client,
    as_bool, date_windows, load_config,

Votre propre paquet d’aides. En bref : DataLake lit et écrit des fichiers dans Silo, DHIS2Client parle à DHIS2, load_config lit le YAML et remplace les ${...}, date_windows découpe une rétrospective en fenêtres mensuelles, run_dbt lance dbt et renvoie son résumé, send_email envoie les alertes. Détails dans la section hmis.py ci-dessus.

    
PROJECT_DIR = Path(__file__).resolve().parent
DEFAULT_CONFIG = "ingestion_config.yml"
Le dossier où se trouve ce fichier, et le nom de configuration par défaut. Se baser sur le dossier du fichier lui-même permet au pipeline de fonctionner quel que soit le répertoire d’où vous le lancez.

  


  

    
Pourquoi seul le chemin de la configuration circule. Chaque flow et chaque tâche reçoit config_path (une chaîne de caractères) et appelle lui-même load_config, au lieu de recevoir toute la configuration. Prefect stocke les paramètres d’exécution et les affiche dans l’interface : faire circuler des mots de passe les ferait fuiter. Un chemin peut être stocké sans risque.

  


  
Chaque fonction, une par une

  
Ouvrez une fiche pour une explication en langage simple. Les tâches ont des réglages de relance, indiqués dans les en-têtes des fiches car ils comptent en cas d’échec.

Si vous passez ingestion_config.yml, cela devient PROJECT_DIR/ingestion_config.yml. Les chemins absolus sont laissés tels quels. Les deux flows l’appellent en premier : toutes les étapes suivantes reçoivent donc un chemin valable de n’importe où.

Parcourt cfg["datasets"] et renvoie l’entrée dont la key correspond. Si rien ne correspond, elle lève KeyError: Dataset 'x' not found in config. Une cause fréquente : avoir passé l’identifiant DHIS2 au lieu de la clé.

Prend transform.projects (dbt/lake, dbt/warehouse) et résout les chemins relatifs par rapport au dossier du fichier de configuration : dbt démarre ainsi toujours au bon endroit.


    
prepare_lake(config_path)tâcheVérifie que le bucket existe. 2 relances, à 15 secondes d’intervalle.
      
Construit un DataLake à partir de la configuration et appelle ensure_bucket(). Renvoie le nom du bucket pour le journal. Si Silo est brièvement injoignable, les relances lui laissent le temps de revenir.


    
get_server_time(config_path)tâcheDemande l’heure à DHIS2. 3 relances, à 30 secondes d’intervalle.
      
Cet horodatage devient le watermark de l’exécution. Le flow le lit avant d’extraire quoi que ce soit. Si un établissement modifie une valeur pendant l’exécution, cette modification est plus récente que le watermark : la prochaine exécution incrémentale la récupérera. Utiliser l’horloge de DHIS2 évite les décalages avec celle de votre machine.

Ce que fait une exécution

  
Voici une exécution nocturne, depuis les 02 h 00 jusqu’à la dernière ligne du journal.

  
    
    
  1. Prefect démarre le flow
    Le cron 0 2 * * *, à l’heure de Kigali, se déclenche. Un worker prend l’exécution dans le pool et charge dataset_ingestion.py depuis le dossier du projet. 02 h 00 à Kigali, c’est 00 h 00 UTC : l’identifiant d’exécution commence donc par l’heure UTC, par exemple 20261104T000000Z.
    2. 
    
  2. Préparation
    prepare_lake confirme l’existence du bucket. get_server_time récupère le watermark. Quatre tâches ingest_metadata déposent les dictionnaires en parallèle.
    3. 
    
  3. Chaque jeu de données, l’un après l’autre
    plan_requests choisit les appels. extract_data_values les effectue (jusqu’à 4 à la fois) et dépose chaque réponse. update_watermark avance le signet.
    4. 
    
  4. Reçu et barrière
    write_manifest enregistre le résumé de l’exécution. Si un jeu de données a échoué, le flow lève une erreur ici et l’exécution s’arrête.
    5. 
    
  5. dbt lake, puis dbt warehouse
    Landing devient du Parquet staging et intermediate dans Silo, puis des marts gold dans ClickHouse. Un test en échec arrête l’exécution avant que gold soit touché. Les sections dbt qui suivent expliquent chaque étape.
    6. 
    
  6. Documentation et fin
    La documentation dbt est rafraîchie. Si quelque chose a échoué ou planté plus tôt, notify_failure a déjà écrit à l’équipe.
    7.

dbt : de landing au reporting

  
Après l’ingestion, tout est dbt. Prefect ne modifie plus jamais les données ; il se contente de démarrer dbt deux fois, une par projet, et d’attendre la réponse.


  
dbt en cinq minutes

  
    
    
  1. Un modèle est un SELECT dans un fichier
    Chaque fichier .sql de models/ contient un SELECT. dbt l’enveloppe dans la bonne instruction pour construire une table, une vue ou un fichier Parquet. Vous n’écrivez jamais CREATE TABLE.
    2. 
    
  2. ref() et source() dessinent la carte
    {{ ref('stg_dhis2__data_values') }} signifie « utilise ce modèle ici ». {{ source('landing', 'data_values') }} signifie « utilise des données brutes que dbt n’a pas construites ». À partir de ces appels, dbt déduit l’ordre de construction.
    3. 
    
  3. La matérialisation dit comment stocker
    Dans ce projet : external dans le lake (un fichier Parquet dans Silo), view pour les modèles « porte d’entrée » de ClickHouse, table (MergeTree) pour gold.
    4. 
    
  4. Les tests vérifient le résultat
    Les tests génériques s’écrivent dans des fichiers .yml (unique, not_null, relationships, accepted_values). Les tests singuliers sont des fichiers .sql dans tests/ qui renvoient les mauvaises lignes ; aucune ligne signifie réussite.
    5. 
    
  5. dbt build fait tout, dans l’ordre
    dbt build construit chaque modèle, le teste, puis passe à ce qui en dépend. Une erreur de modèle ou un test en échec renvoie un code de sortie non nul, que run_dbt transforme en exécution échouée.
    6.

Staging : les premières transformations

  
Un modèle staging par source. Ils renomment, nettoient les espaces, typent et dédoublonnent. Ils ne font pas de jointures. Le plus gros est stg_dhis2__data_values, construit comme une chaîne de petites étapes (CTE), chacune faisant un seul travail.

  

    
values_ as (
  select dataset as dataset_key, data_set_id,
         run_id, mode as load_mode,
         period as payload_period, ...,
         unnest(dataValues) as dv
  from payloads )
1. Déplier. unnest transforme la liste de valeurs de chaque charge utile en une ligne par valeur, en gardant l’exécution, le mode et les champs du niveau charge utile.

    
restored as (
  select ...,
    coalesce(dv.period, payload_period) as period,
    coalesce(dv.orgUnit, payload_org_unit) as org_unit_id,
    coalesce(dv.attributeOptionCombo,
             payload_attribute_option_combo) ...
2. Restaurer. Si DHIS2 a remonté un champ au niveau de la charge utile, la valeur elle-même n’en a pas. coalesce prend le champ propre à la valeur quand il existe, sinon celui de la charge utile.

    
max(case when load_mode = 'full' then run_id end)
  over (partition by data_set_id, period)
  as latest_full_run_id
...
where latest_full_run_id is null
   or run_id >= latest_full_run_id
3. Règle de l’instantané. Une exécution full est une image complète des périodes qu’elle couvre. Pour chaque jeu de données et chaque période, on ne garde que les lignes à partir de la dernière exécution full. Les lignes des exécutions plus anciennes sont écartées : c’est ainsi qu’une valeur supprimée dans DHIS2 disparaît après la prochaine actualisation complète. Exemple détaillé plus bas.

    
qualify row_number() over (
  partition by data_set_id, data_element_id, period,
    org_unit_id, category_option_combo_id,

Le fichier prefect.yaml

  
Ce fichier transforme le flow en déploiements nommés et planifiables. Rien ne s’exécute directement à partir de lui : vous l’enregistrez avec prefect deploy et Prefect retient ce que vous avez enregistré.


  
La configuration en tête de fichier

  

    
name: hmis-data-ingestion
prefect-version: 3.4.0
build: null
push: null
Le nom du projet et la version de Prefect pour laquelle il a été écrit. build et push sont désactivés car rien n’a besoin d’être empaqueté : le worker exécute le code directement depuis un dossier du disque.

    
pull:
  - prefect.deployments.steps.set_working_directory:
      directory: "{{ $HMIS_PROJECT_DIR }}"
Ce que fait le worker avant chaque exécution : se placer dans le dossier désigné par la variable d’environnement HMIS_PROJECT_DIR. Ce dossier doit contenir dataset_ingestion.py.

    
definitions:
  work_pools:
    hmis_pool: &hmis_pool
      name: hmis-process-pool
      work_queue_name: default
  tags: &tags
    - hmis
    - dhis2
    - datalake
    - dbt
Ancres. &hmis_pool étiquette un bloc pour le réutiliser plus loin avec *hmis_pool. On écrit le pool et les tags une seule fois, puis on les réutilise dans chaque déploiement. Changer le nom du pool à un endroit le change partout.

Les ancres réutilisées du haut : les tags, et le pool dont le worker exécutera le déploiement.

Un profil permet de pointer la même ligne de commande vers différents serveurs Prefect. Le worker est la pièce qu’on oublie : sans lui, les exécutions planifiées sont créées mais personne ne les réalise. Le worker lit aussi MINIO_*, CLICKHOUSE_* et DBT_EXECUTABLE dans le fichier .env du dossier du projet.


  
Le script du worker : start_worker.sh

  
setup.sh fait déjà pour vous l’installation initiale ci-dessus. Ce que vous lancez chaque jour, c’est le worker, via un petit script.

Indique au worker où se trouve le code. L’étape pull de prefect.yaml lit cette variable. Le script se place d’abord dans son propre dossier : il fonctionne donc de n’importe où.

L’environnement virtuel contenant Prefect et les paquets du pipeline. Remplacez-le avec HMIS_VENV si le vôtre est ailleurs.

Démarre le worker sur le profil hmis, à l’écoute du pool hmis-process-pool. --limit 1 signifie qu’il exécute une seule exécution de flow à la fois : deux exécutions n’écrivent donc jamais en même temps dans le lake.

Lancer dbt seul : un déploiement dbt uniquement

  
Aujourd’hui, chaque déploiement lance hmis_pipeline, qui commence toujours par ingérer. L’interrupteur with_dbt=false saute dbt, mais aucun interrupteur ne saute l’ingestion. Si vous venez de modifier un modèle dbt et voulez reconstruire sans rappeler DHIS2, vous avez deux possibilités.


  
Option 1 : lancer dbt à la main

  
Pas besoin de Prefect. dbt a besoin des secrets de .env dans son environnement : exportez-les d’abord.

  
source ~/venvs/hmis-dbt/bin/activate
cd ~/hmis_ingestion
set -a; . ./.env; set +a          # HMIS_HASH_SALT, MINIO_*, CLICKHOUSE_*, HMIS_DUCKDB_PATH

cd dbt/lake      && dbt debug && dbt build     # landing -> staging -> intermediate
cd ../warehouse  && dbt debug && dbt build     # intermediate -> gold

  
dbt debug vérifie le profil et la connexion avant la construction. Lancez le projet lake en premier : le warehouse lit les fichiers qu’il écrit.


  
Option 2 : ajouter un petit flow et le déployer

  

    
Une suggestion, qui ne fait pas partie du dépôt. Le code ci-dessous réutilise les tâches existantes dbt_build et dbt_docs. Je ne l’ai pas exécuté : testez-le avant de vous y fier.

  

  
Ajoutez ceci à la fin de dataset_ingestion.py, au-dessus de la fonction _parse_args :

  
@flow(
    name="hmis-dbt-only",
    log_prints=True,
    on_failure=[notify_failure],
    on_crashed=[notify_failure],
)
def hmis_dbt_only(config_path: str = DEFAULT_CONFIG) -> dict:
    """Rebuild lake then warehouse from what is already in landing."""
    config_path = _resolve_config(config_path)
    result = {}
    for project in ("lake", "warehouse"):
        result[project] = dbt_build(config_path, project)
    return result

  
Ajoutez ensuite un déploiement à prefect.yaml et enregistrez-le :

  
  - name: hmis-dbt-only
    description: Rebuild dbt lake and warehouse from existing landing data; no ingestion.
    entrypoint: dataset_ingestion.py:hmis_dbt_only
    tags: *tags
    parameters:
      config_path: ingestion_config.yml
    work_pool: *hmis_pool
    concurrency_limit: 1

  
prefect deploy --name hmis-dbt-only
prefect deployment run "hmis-dbt-only/hmis-dbt-only"

  
Notez le nom d’exécution : c’est nom-du-flow/nom-du-déploiement, et ici le flow s’appelle hmis-dbt-only. Le hook d’e-mail d’échec fonctionne sans changement, car il n’a besoin que du paramètre config_path du flow.

Do DHIS2 aos painéis: como funciona a plataforma de dados HMIS

  
Todas as noites, este projeto copia dados de saúde do DHIS2, deposita-os intactos num data lake, limpa-os e junta-os com o dbt, cria tabelas de reporting no ClickHouse e apresenta-as no Metabase. Este guia explica cada passo, cada função e cada ficheiro, e mostra como criar e executar o seu próprio deployment Prefect ou modelo dbt.


  

    

      
DHIS2
As unidades sanitárias introduzem aqui as suas contagens. Nós apenas lemos.

      
Landing
Cópias exatas do que o DHIS2 enviou, guardadas no Silo.

      
Staging e intermediate
O dbt limpa, junta e remove os dados pessoais.

      
Marts gold
Tabelas do ClickHouse preparadas para reporting.

      
Painéis
O Metabase lê o gold, só em leitura.

    

    

      
O Prefect inicia a execução de acordo com o agendamento, repete o que falha, para na primeira falha e envia e-mail à equipa

      
1 Ingestão: o Python copia o DHIS2 para o landing

      
2 dbt lake: staging e depois intermediate

      
3 dbt warehouse: marts gold

      
4 O Metabase consulta o gold

    

  







  
Visão geral

  
Imagine o sistema de água de uma cidade. O DHIS2 é a nascente. A área de landing é um depósito de captação que guarda a água exatamente como chegou, etiquetada com o dia de entrada. O Staging e o intermediate são a estação de tratamento, onde o dbt filtra, padroniza e mistura os dados. Os marts gold são as torneiras, e o Metabase é onde as pessoas enchem os seus copos. O Prefect é a sala de controlo: abre as válvulas a horas, repara quando uma bomba falha e pára a estação antes que água suja chegue a uma torneira.


  
Três regras que o desenho segue

  
Primeiro aterrar, depois alterar. A ingestão nunca transforma nada. Guarda cada resposta do DHIS2 tal como foi recebida, para que possa sempre reproduzir o histórico. Toda a limpeza acontece no dbt.

  
Parar à primeira falha. Primeiro a ingestão, depois o dbt lake, depois o dbt warehouse. Se um passo falhar, os seguintes não correm, pelo que o gold nunca é reconstruído a partir de dados maus. Os painéis continuam a mostrar a última execução boa e a equipa recebe um e-mail.

  
Os dados pessoais ficam pelo caminho cedo. Os valores do DHIS2 trazem o nome da pessoa que os introduziu e um comentário em texto livre. O staging aplica hash ao nome, o intermediate remove ambos, e o ClickHouse e o Metabase nunca os veem.

Porque é que o gold vive apenas no ClickHouse

  
O Silo guarda os dados detalhados e reutilizáveis (até ao intermediate) como ficheiros baratos que qualquer motor consegue ler. O gold é um conjunto de agregados que o ClickHouse constrói a partir deles em segundos, pelo que uma segunda cópia no lake só teria de ser mantida em sincronia. Se o ClickHouse se perder, executar dbt build em dbt/warehouse recria o gold a partir do Silo.

Palavras que vai encontrar

  
A maior parte da confusão dos principiantes é vocabulário. Percorra esta lista agora e volte quando uma palavra o fizer tropeçar.

  
Orquestração

  

    
Flow
Uma função Python marcada com @flow. O Prefect regista cada execução. Um flow pode chamar outros flows (subflows).

    
Task
Uma função mais pequena marcada com @task, chamada a partir de um flow. Uma task pode repetir-se sozinha quando falha.

    
Execução (run)
Uma execução de um flow, com a sua própria página e registos na interface do Prefect.

    
Deployment
Uma instrução guardada: «executar este flow, com estes parâmetros, neste agendamento.» Definida em prefect.yaml.

    
Parâmetros
As entradas de um flow, como mode ou datasets. Um deployment fixa-as; pode substituí-las em cada execução.

    
Agendamento
Uma expressão cron mais um fuso horário que diz ao Prefect quando iniciar um deployment.

    
Work pool e worker
O pool é uma fila de execuções à espera de acontecer. O worker é um programa que mantém em execução, que vai buscar as execuções e as executa.

    
Watermark
Um marcador: a hora do servidor DHIS2 da última execução bem-sucedida. A execução incremental seguinte pede apenas os valores alterados desde então.

    
Manifesto
Um pequeno recibo JSON escrito no fim de cada execução: o que foi aterrado, o que falhou.

    
run_id
Um carimbo de data/hora como 20261104T000000Z que identifica tudo o que uma execução escreveu.

  

  
Armazenamento

  

    
Data lake
Um bucket de ficheiros, barato e legível por qualquer motor. Aqui é o Silo, um fork mantido do MinIO com a mesma API S3.

    
Bucket e prefixo
O bucket é a pasta de nível superior (hmis-datalake). Um prefixo é um caminho dentro dele, como landing/dhis2/.

    
Landing, staging, intermediate, gold
As camadas (por vezes chamadas camadas medallion). Cada uma é mais limpa e mais refinada do que a anterior.

    
Parquet
Um formato de ficheiro compacto, tipificado e orientado a colunas, que o DuckDB e o ClickHouse leem rapidamente.

    
Partição ao estilo Hive
Pastas com o nome key=value, como run_id=…/mode=full/. O DuckDB transforma-as em colunas.

    
ClickHouse
Uma base de dados analítica rápida. Contém apenas os marts gold.

    
DuckDB
Um pequeno motor analítico que corre dentro do processo do dbt. Lê e escreve Parquet no Silo.

  

  
Transformação

  

    
dbt
Uma ferramenta que transforma ficheiros SQL SELECT em tabelas ou ficheiros, pela ordem certa, e testa-os.

    
Modelo
Um ficheiro .sql com um único SELECT. O dbt constrói-o como tabela, vista ou ficheiro.

    
Fonte
Dados que o dbt lê mas não constrói. Aqui, os ficheiros do landing.

    
ref() e o source()
Funções Jinja que apontam para outro modelo ou fonte. Indicam ao dbt a ordem de construção.

    
Materialização
Como um modelo é armazenado: external (um ficheiro Parquet), view, ou table.

    
Teste
Uma regra verificada depois de um modelo ser construído. Um teste que falha pára o pipeline; um aviso é apenas registado.

    
Macro
Uma função Jinja reutilizável, como hash_pii(). Vive em macros/.

    
Mart
Uma tabela final para reporting. As tabelas «fact» guardam medidas; uma «dimensão» descreve coisas como unidades organizacionais.

    
Granularidade (grain)
O que uma linha representa, como «um distrito, um mês, um elemento de dados».

    
Chave substituta (surrogate key)
Um id único inventado, aqui um hash md5 das colunas da chave natural.

  

  
Privacidade e acesso

  

    
PII
Dados pessoais. Aqui: storedBy (quem introduziu um valor) e comment (texto livre).

    
Hash e salt
Um hash transforma um nome num código ilegível. O salt é um segredo adicionado primeiro, para que ninguém consiga reverter o código adivinhando nomes.

    
Named collection
Uma definição do ClickHouse que guarda o endereço e as chaves do lake, para que o SQL possa dizer s3(silo, …) sem palavra-passe.

    
Variável de ambiente
Uma definição com nome fora do código, como MINIO_ENDPOINT. Os segredos vivem em .env.

    
YAML
Um formato de texto para definições. A indentação importa: dois espaços significam «isto pertence à linha acima».

    
Metabase
A ferramenta de painéis que consulta o gold.

O que faz uma execução

  
Eis uma execução noturna desde o relógio marcar as 02:00 até à última linha de registo.

  
    
    
  1. O Prefect inicia o flow
    O cron 0 2 * * * à hora de Kigali dispara. Um worker retira a execução do pool e carrega dataset_ingestion.py da pasta do projeto. As 02:00 em Kigali são as 00:00 UTC, pelo que o id da execução começa com a hora UTC, por exemplo 20261104T000000Z.
    2. 
    
  2. Preparação
    prepare_lake confirma o bucket. get_server_time obtém o watermark. Quatro tasks ingest_metadata aterram os dicionários em paralelo.
    3. 
    
  3. Cada conjunto de dados, um de cada vez
    plan_requests escolhe as chamadas. extract_data_values faz-as (até 4 de cada vez) e aterra cada resposta. update_watermark avança o marcador.
    4. 
    
  4. Recibo e barreira
    write_manifest guarda o resumo da execução. Se algum conjunto de dados falhou, o flow levanta uma exceção aqui e a execução pára.
    5. 
    
  5. dbt lake e depois dbt warehouse
    O landing torna-se Parquet staging e intermediate no Silo e depois marts gold no ClickHouse. Um teste que falhe pára a execução antes de o gold ser tocado. As secções dbt abaixo explicam cada passo.
    6. 
    
  6. Documentação e conclusão
    A documentação dbt é atualizada. Se algo tivesse falhado ou bloqueado antes, notify_failure já enviou e-mail à equipa.
    7.

dbt: do landing ao reporting

  
Depois da ingestão, tudo é dbt. O Prefect nunca volta a alterar os dados; apenas inicia o dbt duas vezes, uma por projeto, e espera pela resposta.


  
dbt em cinco minutos

  
    
    
  1. Um modelo é um SELECT num ficheiro
    Cada ficheiro .sql em models/ contém um SELECT. O dbt envolve-o na instrução certa para construir uma tabela, uma vista ou um ficheiro Parquet. Nunca escreve CREATE TABLE.
    2. 
    
  2. ref() e source() desenham o mapa
    {{ ref('stg_dhis2__data_values') }} significa «usar aqui esse modelo». {{ source('landing', 'data_values') }} significa «usar dados em bruto que o dbt não construiu». A partir destas chamadas, o dbt calcula a ordem pela qual constrói as coisas.
    3. 
    
  3. A materialização diz como armazenar
    Neste projeto: external no lake (um ficheiro Parquet no Silo), view para os modelos de entrada do ClickHouse, table (MergeTree) para o gold.
    4. 
    
  4. Os testes verificam o resultado
    Os testes genéricos são escritos em ficheiros .yml (unique, not_null, relationships, accepted_values). Os testes singulares são ficheiros .sql em tests/ que devolvem as linhas más ; nenhuma linha significa que passou.
    5. 
    
  5. O dbt build faz tudo por ordem
    dbt build constrói cada modelo, testa-o e depois passa ao que depende dele. Um erro de modelo ou um teste que falhe devolve uma saída diferente de zero, e run_dbt transforma isso numa execução falhada.
    6.

Executar o dbt isoladamente: um deployment só com dbt

  
Hoje, cada deployment executa hmis_pipeline, que ingere sempre primeiro. O interruptor with_dbt=false salta o dbt, mas não há nenhum interruptor que salte a ingestão. Se acabou de editar um modelo dbt e quer reconstruir sem voltar a chamar o DHIS2, tem duas opções.


  
Opção 1: executar o dbt à mão

  
Não é preciso Prefect. O dbt precisa dos segredos de .env no seu ambiente, por isso exporte-os primeiro:

  
source ~/venvs/hmis-dbt/bin/activate
cd ~/hmis_ingestion
set -a; . ./.env; set +a          # HMIS_HASH_SALT, MINIO_*, CLICKHOUSE_*, HMIS_DUCKDB_PATH

cd dbt/lake      && dbt debug && dbt build     # landing -> staging -> intermediate
cd ../warehouse  && dbt debug && dbt build     # intermediate -> gold

  
dbt debug verifica o perfil e a ligação antes de construir. Execute primeiro o projeto lake: o warehouse lê os ficheiros que ele escreve.


  
Opção 2: acrescentar um pequeno flow e fazer o seu deploy

  

    
Uma sugestão, não faz parte do repositório. O código abaixo reutiliza as tasks existentes dbt_build e o dbt_docs . Não o executei, por isso teste-o antes de depender dele.

  

  
Acrescente isto ao fim de dataset_ingestion.py, acima da função _parse_args :

  
@flow(
    name="hmis-dbt-only",
    log_prints=True,
    on_failure=[notify_failure],
    on_crashed=[notify_failure],
)
def hmis_dbt_only(config_path: str = DEFAULT_CONFIG) -> dict:
    """Rebuild lake then warehouse from what is already in landing."""
    config_path = _resolve_config(config_path)
    result = {}
    for project in ("lake", "warehouse"):
        result[project] = dbt_build(config_path, project)
    return result

  
Depois acrescente um deployment a prefect.yaml e registe-o:

  
  - name: hmis-dbt-only
    description: Rebuild dbt lake and warehouse from existing landing data; no ingestion.
    entrypoint: dataset_ingestion.py:hmis_dbt_only
    tags: *tags
    parameters:
      config_path: ingestion_config.yml
    work_pool: *hmis_pool
    concurrency_limit: 1

  
prefect deploy --name hmis-dbt-only
prefect deployment run "hmis-dbt-only/hmis-dbt-only"

  
Note o nome da execução: é nome-do-flow/nome-do-deployment, e aqui o flow é hmis-dbt-only. O hook de e-mail de falha funciona sem alterações, porque só precisa do config_path .

-- Measles doses given per chiefdom and month (Child Health, monthly).
-- Grain: month x district x chiefdom.

select
    toDate(ifNull(period_start_date, toDate32('1970-01-01'))) as month,
    ifNull(district_name, '')   as district_name,
    ifNull(chiefdom_name, '')   as chiefdom_name,
    sum(value_numeric)          as measles_doses,
    uniqExact(org_unit_id)      as facilities_reporting
from {{ ref('lake_dhis2__data_values') }}

Escolher o que o dbt executa

  

    
ComandoO que faz

    
      
dbt buildTodos os modelos e todos os testes, por ordem de dependência. É o que o pipeline executa.

      
dbt build --select o_meu_modeloApenas esse modelo e os seus testes.

      
dbt build --select +o_meu_modeloO modelo e tudo o que está a montante dele.

      
dbt build --select o_meu_modelo+O modelo e tudo o que está a jusante dele.

      
dbt build --exclude o_meu_modeloTudo exceto esse modelo.

      
dbt run ou dbt testApenas construir modelos ou apenas executar testes.

      
dbt compileEscreve o SQL final em target/compiled/ sem o executar. Útil para ver no que se transformou ref() .

      
dbt debugVerifica o perfil e a ligação.

      
dbt docs generate --staticReconstrói o site de documentação de um só ficheiro (o pipeline faz isto após cada execução bem-sucedida).

    
  






  
Quando algo corre mal

  
Comece pela interface do Prefect: abra a execução, leia a linha vermelha do registo e faça corresponder abaixo. Verifique também a caixa de entrada de e-mail em localhost:8025 : as execuções falhadas enviam uma mensagem com o motivo e uma ligação.

  

    
O que vêCausa provávelO que fazer

    
      
Uma página web (Silo, ClickHouse, Prefect, Metabase, docs, Mailpit) não carregaO Ubuntu encerrou, levando consigo o Docker.Abra um terminal Ubuntu; os contentores arrancam em segundos. Verifique com docker compose ps.

      
Não há execuções agendadas; as execuções ficam em Scheduled, Pending ou LateO worker não está em execução, ou o nome do pool é diferente.Inicie ./start_worker.sh. No Prefect, Work Pools, hmis-process-pool deve aparecer Online.

      
O novo deployment não está na interfaceO ficheiro foi guardado mas nunca registado, ou a CLI aponta para outro servidor Prefect.Execute prefect deploy --name .... Verifique se prefect profile ls mostra hmis como ativo.

      
A execução falha antes de qualquer task: ficheiro ou diretório não encontradoHMIS_PROJECT_DIR não está definido onde o worker corre.Inicie o worker com ./start_worker.sh, que o define.

      
ModuleNotFoundError: hmisO worker foi iniciado fora do ambiente virtual de ingestão.Use ./start_worker.sh, que usa ~/venvs/hmis-ingestion.

      
A execução falha logo com um erro de parâmetroUm nome de parâmetro mal escrito, ou o tipo errado (por exemplo datasets como texto em vez de lista).Compare com os cinco parâmetros. As listas precisam de um traço por item.

      
Dataset 'x' not found in configO valor em datasets não é uma key da configuração (muitas vezes é o id do DHIS2).Use a key, como child_health.

      
O DHIS2 devolve 404 ou está muito lentoO servidor play muda de versão e é partilhado.Escolha uma instância atual em play.dhis2.org e defina DHIS2_BASE_URL em .env.

      
O dbt falha com «HMIS_HASH_SALT must be set»O salt está em falta em .env, ou .env não foi exportado ao executar o dbt à mão.Adicione o salt; execute set -a; . ./.env; set +a antes do dbt.

      
O passo dbt falha com command not foundDBT_EXECUTABLE não é o dbt do seu próprio ambiente virtual.Defina o caminho completo em .env (setup.sh faz isto).

      
Um teste dbt falha e a execução páraOs dados violaram uma regra. O gold não foi reconstruído, pelo que os painéis mostram a última execução boa.Leia as linhas do dbt no registo do Prefect. Execute o SQL do teste para ver as linhas más. Corrija os dados ou o modelo e depois execute de novo.

      
A ingestão funcionou mas os painéis não mudaramA execução tinha with_dbt: false, ou um passo anterior falhou.Verifique os parâmetros da execução e procure as linhas do dbt no registo.

      
«Port already in use» ao iniciar o DockerOutra stack ocupa as portas predefinidas.Esta stack já usa 9100, 9101, 8124, 9010, 4200, 3010, 8085, 8025 e 1025 por esse motivo. Pare o que estiver a ocupar a porta.

      
Não há painel HMIS Overview no MetabaseÉ construído em último lugar por setup.sh, e ignorado com --skip-data.Carregue dados e depois execute python metabase/setup_metabase.py.

      
Não chega nenhum e-mail de falhaAs definições SMTP são as predefinidas locais.Veja o Mailpit, ou defina as variáveis SMTP_* em .env.

    
  

  
Um facto tranquilizador: os ficheiros do landing nunca são sobrescritos e o watermark só avança após sucesso, pelo que uma execução falhada pode ser repetida em segurança. Não perderá dados nem os contará a dobrar; o dbt remove duplicados.
